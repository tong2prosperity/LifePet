## 2026-08-13 产品重置检查点（历史）

用户批准把近期产品重新冻结为更直接的核心：真实睡眠与活动使 Pibo 本身发生可见
变化，头顶生长并成熟一枚可拔取的 `bo`，累计生活继续给 Pibo 或共同森林留下永久
成长。近期目标不是继续制作事件 04–21，而是先验证用户能否立即理解“我的健康数据
正在改变 Pibo”、是否回来拔取第一枚 `bo`，以及累计有效日后是否仍愿意回来。

本次确认同时改变或重开以下边界：

- 正向变化必须直接落在 Pibo 身上，而不能只绕到库存、设施、返航和故事资格；这也是
  未来 Shadow Pibo 能够映射好友 Pibo 状态的基础；
- Pibo 可以受苦，决定 027 的绝对禁止已重新打开；具体触发、程度、恢复、缺失数据与
  反强迫边界尚未拍板，当前不得自行扩写成死亡、不可逆损失、权限惩罚或负罪机制；
- 餐食相机、Walk Doodle 与 Shadow Pibo 都确定保留在产品路线图中，可能不属于这个
  极简 MVP；所属版本、收费方式及与共同物件的关系需要继续论证；
- 用户认为“共同物件解锁新能力”可能有意义，决定 032 的现行实现暂不撤销，但必须
  重新验证因果是否直观、解锁时机是否妨碍功能发现，以及付费与 `bo` 解锁如何分工；
- Home 的真实工程已经是固定单屏森林，没有 Studio/Gym 页面或横向漫游。`Games/`
  只是关闭的工程库存，不等同于 Gym。旧文档中的 `studio ← home ← gym` 不再有效。

2026-08-15 又冻结了首期主状态生命周期的简化原则：不建立复杂状态优先级矩阵，以最近
一次有效状态变化覆盖此前状态。睡眠不足先触发疲惫、随后完成运动时，Pibo 应转为精力
充足。精力充足持续保持，直到之后另一个有效主状态变化出现；运动时间窗结束或步数跨日
重置不构成自动回落稳定。初醒阶段结束且期间没有新的有效健康事件时，Pibo 进入稳定，
不恢复入睡前状态。刚结束的主要睡眠如果触发疲惫，该结果在初醒期间保留，初醒结束后
进入疲惫；恢复良好则对称地在初醒结束后进入精力充足。有效状态事件按事实发生时间采用
最新者，同状态新事件只更新原因并播放事件反应；条件过期不自动回落，首期除初醒 60 分钟
外不增加主状态最短保持或冷却。睡眠被更晚的真实运动／活动事件覆盖后视为中断，不在原定
醒来时间凭空播放初醒。迟到的当前醒来周期睡眠结果可以修正临时回退，但历史回填不能以
同步时间覆盖更新的真实事件。该生命周期已经由 `pibo-core 0.13.2` 统一实现，并同步到
iOS exact pin 与 HarmonyOS submodule；双端只负责收集带发生时间的事实、持久化快照和表现。

睡眠／初醒资源按吊床拥有状态选择：有吊床用吊床资源，无吊床用地面资源。2026-08-16
已完成 `pibo-state-sleeping-ground-idle-a` 的最新几何与 4.8 秒低幅呼吸循环；无吊床睡眠不再
回退稳定。无吊床且 Core 在 waking 中保留的待落地结果为 `tired + insufficientSleep` 时，
App 直接选择 `pibo-state-waking-ground-behavior-recovering` 的 7.2 秒恢复不足循环，不在平台端
复制睡眠阈值。拥有吊床时仍使用现有吊床初醒资源。普通无吊床 waking 在本期仍采用稳定姿态
作为明确回退，但 Core 语义、初醒计时和交互保护始终保持 waking。

2026-08-16 已撤回未审定的精力充足姿态与四个附加关键帧：它们不再进入跨端
`PiboCharacterData.json`、iOS 运行时可用集合、首页 Debug Panel 或 Character Lab。Core 的
`energetic` 仍是有效健康语义，当前 App 统一回退到稳定姿态，不借用活动里程碑庆祝，也不
依赖任何 energetic 美术 ID。草稿母版可以保留在媒体源仓库中继续设计，但重新进入 App 前
必须先完成美术审核和动画编排。

状态数值也已于 2026-08-15 冻结：单晚低于 `max(个人睡眠基线 × 65%, 4.5 小时)` 触发
疲惫，连续两晚都低于基线 80% 也触发；一晚达到基线 95% 即从疲惫恢复。良好睡眠要求
高于基线 30 分钟且至少 6.5 小时，活动里程碑改为 8,000 步；无个人基线时使用 7 小时，
动态作息仍要求至少四晚且规律性达到 60，近期运动首次发现窗口仍为结束后 3 小时。上述
阈值、8,000 步内容键和双端文案已按 Core 发布顺序完成迁移；3 小时发现判断也由 Core
提供，平台端没有复制窗口数值。

本检查点尚未授权关闭 Release 中现已开启的餐食相机或 Walk Doodle；用户使用了
“可能不是这个 MVP”的表述，需在版本分层讨论后再改发布开关。

## 2026-08-17 首版改造确认点

用户批准 `docs/product-strategy-202608/` 的修订方案，当前可以进入首版改造：

- 基础餐食相机首日可见并与补梦风铃门控解耦。拍摄可选，不是三餐任务；返回森林后由

- 首版不做因未打开 App 触发的冰封／休眠。持续健康数据异常使用 `dataUnknown`，瞬时网络、

- Shadow Pibo 的隐私风险不作为产品阻塞项，但 Shadow Pibo 仍不进入本轮 P0；
- Day 0–7 按真实事件推进，不承诺固定成熟日，不使用连续签到或强制三餐任务。

## 2026-08-19 情境闲聊冻结点

用户确认将 Pibo 的拍一拍改为“状态驱动的情境短句系统”，完整规则见
[`decisions/033-Pibo情境闲聊与拍一拍调度机制.md`](decisions/033-Pibo%E6%83%85%E5%A2%83%E9%97%B2%E8%81%8A%E4%B8%8E%E6%8B%8D%E4%B8%80%E6%8B%8D%E8%B0%83%E5%BA%A6%E6%9C%BA%E5%88%B6.md)。

- 拍一拍是一次接触，不是随机奖励或无限对话；一次有效点击必须回应，正常说话无次数上限。
- 按 `state + context` 进入文案池；新状态／新事件在下一次有效点击优先回应一次，不主动弹出。
- 池内只按游标顺序循环，不随机，不用手工 ID 去重；实时变量或故事阶段不满足时跳过候选。
- 气泡时长与冷却相同；冷却中点击忽略。当前版本只按中文体验确定时长，Reduce Motion 不改变冷却。
- 新 Core 主状态或离开首页立即清除气泡和冷却；同页 Sheet／其他功能不提前清除。
- 文案与语义动作集中为一个 JSONL 著作源，最小字段为 `state / context / action / speaker / lines`，
  单句只有 `text` 和可选 `stages`。
- 旧 Pat V2 的概率说话、第三次生气、每 10 分钟／每日上限已被替代。新动作素材不阻塞文字机制，缺失资源留 TODO。
- Pibo 的恒定说话风格已由决定 034 冻结；六个 Core 主状态的首版内容与行为边界现已全部审核通过。
  JSONL、Core 0.14.0 与 HarmonyOS 接入已于 2026-08-22 完成；当时的 iOS TODO 已于 2026-08-25 关闭。

## 2026-08-19 说话风格与中文首发冻结点

用户确认 Pibo 采用“克制的观察型同伴”作为恒定说话风格，完整规则见
[`decisions/034-Pibo恒定说话风格与中文首发.md`](decisions/034-Pibo%E6%81%92%E5%AE%9A%E8%AF%B4%E8%AF%9D%E9%A3%8E%E6%A0%BC%E4%B8%8E%E4%B8%AD%E6%96%87%E9%A6%96%E5%8F%91.md)。

- 游戏感来自情境、连续性和小变化，不来自健康任务、积分话术或高频奖励；
- Pibo 说自己的观察、判断和行动，准确数值、权限、错误和修复方法由系统 UI 说明；
- 六状态只调节注意力、句子完整度和行动倾向，不改变认真、直接、程序化且有自尊的恒定人格；
- 当前 MVP 只制作和验收简体中文，不做英文台词、占位、回退或双语等长适配；
- 现有旧英文资源可保留，但不作为新情境文案真源；未来英文作为独立角色语言设计启动；
- 下一步不是继续讨论抽象风格，而是确定 `stable` 三个首发情境、事实槽位和正式候选台词。

## 2026-08-21 拍一拍微章节机制冻结

用户批准拍一拍不再局限于每次一个互不相关的单句。一个互动单元可以包含两至三句为主的微章节，
每次冷却外的有效点击推进下一句，让 Pibo 把一个具体事项说完。完整数据和中断规则见决定 033。

- 一条 JSONL 记录就是一个完整互动单元，`lines` 是其内部逐拍句子；单句只是 `lines` 长度为一；
- 同一 `state + context` 可以有多条记录并按记录游标循环，不增加 `mode`、文案 ID 或随机权重；
- 第一拍执行 `action`，后续拍只继续文字；末句结束后才移动记录游标并消费事件；
- 主状态改变或离开首页中断；未完成事件以后从第一句重来；同一状态的新事件不抢断正在说的事项；
- 借鉴闲聊花花的具体情境、说话者联想和字面反转，不复制高频拖音与另一套角色人格；
- `energetic.ready` 已明确保留“我现在很有精神。”“你是想看我动一下？”。跑步采用三拍方向；
  里程碑允许“令人刮目相看。”“做得真的不错。”，良好睡眠采用“睡真饱啊。”→“今天又是
  美好的一天。”；`energetic` 后续已按鸿蒙现有运动分类完成审核并实现。
- 跑步 R1 与走路 W1 已选为首版：“你刚才跑步了吗？”→“如果我也开始跑……”→“不知道我的
  肚子多久能小一点。”；“你刚才走路了吗？”→“我也可以散步。”→“围着这里走，算散步吗？”；
- 走路 W2“路上看到什么了？”方向本身可用，但它要求真正的用户回答。当前版本不增加输入框，
  所以冻结“问句契约”：可以用点击已经回答的反应性问句，或由 Pibo 自己继续的疑问；不能提出
  需要用户输入的新问题并假装完成双向对话。
- 骑行 C1 与游泳 S1 已选为首版：“你刚才骑车了吗？”→“骑快一点，风会很大吧。”→“我头上的
  花大概会被吹歪。”；“你刚才游泳了吗？”→“我这么圆……”→“应该很容易浮起来吧。”。
- 高强度／力量归类选择 H1：“你刚才训练了吗？”→“我也跟着做了一下。”→“一下应该也算。”；
  瑜伽／伸展归类选择 Y1：“你刚才在伸展身体吗？”→“我也可以试试。”→“先让我找找腰在哪里。”。

不需要先把一年主线写成完整剧本。进入 MVP 实现前，只需冻结：

1. 世界规则、Pibo 人物、`bo`、伦理和二十一个事件大纲；当前已完成；
2. MVP 真正出现的事件 01–03；事件基础已完成；
3. Onboarding 六场面、完整文案和状态分支；已完成并已在 iOS、HarmonyOS 实现；
4. 第一枚真实 `bo` 的触发、成熟、拔取、库存和失败边界；规则与双平台账本已实现，待真机跨日验收；
5. 新旧叙事迁移范围与 MVP 功能清单；规格和工程迁移已完成，待旧用户升级验收。

达到这一节点后应开始实现 MVP，同时继续深化事件 04 以后内容。后续故事按二十一个事件骨架逐章补充，不等待整年剧本全部完成。

## MVP 明确不做（历史范围记录）

- 付费墙、付费餐食相机、装扮商店、付费皮肤和会员增值；
- 社交、查看其他 Pibo、信号站、实时聊天和共同社群；
- 战斗、PvE、PvP、赛季和除 Walk Doodle 外的其他游戏；
- LLM/VLM 动态生成主线；
- 第一版之外的相机能力；
- 旧坠落求救、找光、命名、语音唤醒、故障逼授权和低活动伤害 Pibo。

这些能力仅保留未来架构与伦理边界，不应提前开发。

## 历史未决问题（不得当作当前状态）

图片、价格、能力与权限边界，展开时先展示「解锁后获得」，完成后以「回到森林」结束。
未拥有时对应入口不出现在主页，显示层与路由层都按 Core capability 再校验；健康授权、
原始健康归档和 `bo` 形成不受物件门控。

当前映射为：吊床开放睡眠回顾与睡醒通知，通知被拒绝时仍可从吊床查看 App 内回顾；
补梦风铃一次开放露珠相机与 Walk Doodle；状态观测仪作为森林物件打开恢复状态 Modal，
只显示「等待数据」或「正在校准」，不借用压力/Wellness 分数；铃兰灯只保留逐盏魔法
点灯。物件 capability、价格、顺序与前置均由 `pibo-core 0.10.0` 统一提供。

2026-08-07 用户再次调整并确认物件映射：补梦风铃一次解锁露珠相机与 Walk Doodle，
不增加新物件；铃兰灯不再承担 Walk Doodle，而与未来单好友 Shadow Pibo 关联。
Shadow Pibo 当前只保留概念和最小扩展接口，不进入 MVP，也不显示空壳入口。此前把
铃兰灯映射到 Walk Doodle 的 Coding Prompt 和视觉稿均已过时。

Onboarding、事件 01–03、第一枚 `bo`、双平台职责、迁移清单与验收用例已经形成 [`23-Onboarding与事件01-03跨平台MVP规格-v0.1.md`](23-Onboarding%E4%B8%8E%E4%BA%8B%E4%BB%B601-03%E8%B7%A8%E5%B9%B3%E5%8F%B0MVP%E8%A7%84%E6%A0%BC-v0.1.md)。决定 031 又收口了两个 P0 架构问题：

- `pibo-core` 是 `bo` 计分和状态转换的唯一规则源，Swift、ArkTS 和 Go 不分别复制算法；
- `bo` 本地优先形成，未登录和离线不阻塞第一枚；登录后幂等合并账本，不在 Onboarding 增加登录；
- 只把接受临时合作以后产生的健康记录用于 `bo`，此前历史只作健康展示。

`pibo-server` 的现有纯计算模型已经等价迁入 Core。iOS 当前仍固定 `pibo-core 0.13.3`；
HarmonyOS 已按本轮平台范围固定到最新 `0.14.0`。`0.13.3` 提供持久主状态生命周期、Core-owned
运动发现窗口、六状态唯一上下文动作与 `bo` 四阶段；`0.14.0` 进一步提供新拍一拍确定性调度。
服务端保留 `bo v1` golden parity 测试。

双平台 MVP 基础接线已经完成：六场面 Onboarding、checkpoint 与中断恢复、旧用户迁移、故事许可、事件 01–03、旧 Pat V2、首页稳定文案键，以及接受临时合作后才开始累计的本地 `bo` 账本均已接入。登录不阻塞启动；健康与通知权限保持独立；第一枚 `bo` 必须来自真实数据；成熟 `bo` 永不过期，也不冻结后续积累。旧 Pat V2 仅是当前代码状态，其日常拍一拍规则已被决定 033 替代。

2026-08-06 工程 review 已补齐数据来源与迁移边界：DEBUG/Demo 健康记录和合成 workout 均有持久化 provenance，不推进事件 02、不铸造 `bo`；真实数据写入同一天时会先移除合成记录，避免未覆盖的 Demo 指标被误认成真实。账本以持久化 `firstEligibleAt` 和 `epoch:*` 日键为准，并兼容旧 `yyyy-MM-dd` 键在跨时区（含 UTC+13/+14）后的迁移。当时 Pat 的 sleep/awake/angry 保护与台词预算校正仍保留为历史实现记录，日常拍一拍后续以决定 033 为准。Onboarding 另存故事 checkpoint，选择“稍后”进入紧凑权限流程不会覆盖之后应恢复的身份或合作场景。iOS Home Widget 已移除旧“活力/静息/心绪”三状态展示，改为当前六状态、同步时间与新运动记录。

同日扩展发布 review 已将工程范围重新对齐决定 022/025：餐食相机与 Walk Doodle 在 iOS、HarmonyOS 都属于首发，Walk Doodle 以独立工具入口发布且不产生 `mini_game_start`，其他小游戏继续关闭。首发相机只允许“选择餐次—真实拍摄—热量识别/记录”，权限拒绝、设备不可用或拍摄失败均不得合成照片或生成餐食记录。发布配置只声明当前功能需要的健康、相机与位置权限；旧语音呼唤和小游戏动作权限不进入发布包。Widget 与运动 Live Activity 统一消费六状态 ID。Onboarding/`bo` 损坏快照按 fail-closed 与 Core 账本规则恢复，重复来源、非法书签、非有限消费和超阈值残余能量均在读取时归一化。

发布链路的进一步 review 又收口了相机生命周期、定位和历史体征语义：双端相机只在取景阶段占用硬件，快速离开/重拍时隔离过期回调并串行释放原生资源，超时或部分初始化失败不会生成餐食；iOS Walk Doodle 在仅获大概位置时不开始记录，并明确说明主动记录才使用精确位置；HarmonyOS 历史体征卡改用压力链路的 RMSSD 与 Core 个人基线分档，不再用平台 SDNN 和固定阈值把单次读数解释成“放松/紧张”。压力提醒的未来时间戳也按时间回拨 fail-open 处理。

2026-08-06 用户决定当前发布暂时关闭“临时合作”机制。iOS 与 HarmonyOS 保留六场面实现，但通过双端发布开关默认关闭，首启恢复此前的 Onboarding 页面；首页与设置不展示合作恢复入口，事件 01–03 的合作故事推进暂停。bo 不再等待“接受临时合作”，以旧 Onboarding 完成时间作为账本边界，并仍从下一个完整自然日开始计入真实健康记录。不得只隐藏按钮而留下空的 acceptedAt，否则新 bo 会停止形成。

双端工程已将“暂停”落实为持久化规则，而不只是隐藏 UI：故事健康观察与事件 03
分别保存暂停后的观察起点和 `bo` lifetime 基线，关闭期间新增的健康事实、成熟或收取
记录不会在未来重开时补推故事。`bo` 账本独立保存 `eligibilityEnabled`、
`firstEligibleAt` 和边界来源 `temporaryCooperation` / `legacyOnboarding` /
`legacyOnboardingMigration`；当前旧 Onboarding 模式继续累计。若未来重新开启临时合作，
尚未接受的用户停止新增 `bo`，但已有进度、成熟物和库存全部保留，接受后再以当时边界
继续。老版本只有 `onboardingDone` 布尔值、没有真实完成时刻时，只能以升级时刻作为
保守边界，并明确标记为 `legacyOnboardingMigration`，不得把它解释为历史精确完成时间。

当前 `PiboCoreBoDailyMetrics` 尚不能表达站立与活动消耗，并且缺失 MVPA 与实测 0 MVPA 无法区分。双端仅在 App 层排除 Core 无法表达的 source-only 日期，没有复制站立算法或阈值。完整支持必须先冻结产品数值、发布新版 Core，再依次更新 iOS exact pin 与 Harmony submodule。

当前工程未决项已经从“实现基础接线”转为真机验收：需要覆盖新用户完整流程、Onboarding
中断恢复、旧用户升级、拒绝或缺失权限、首个完整自然日跨日累计、多枚成熟待拔取、当前
简体中文文案和首页 SpriteKit 表现。英文不属于当前 MVP 验收范围。站立、缺失/零值、行为
能量、来源系数和恢复乘数不得在验收期间绕开 Core 另行解释。

事件 04 的旧启动记录仍可追溯，但不再是当前第一优先级。目标用户、六状态上下文动作、
第一枚真实 `bo`、吊床永久行为、基础相机前置、异常分层和行为型成长已经确认，当前进入
P0 首版改造；事件 04 是否仍需作为独立剧情节点在 P0 后再决定。
