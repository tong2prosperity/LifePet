## 当前已经闭合

- 产品根命题：帮助反复把身体放到后面的人重新看见并重视健康；
- Pibo 定位：共同经历者与镜子，不是宠物、幼儿、被照顾者或健康教练；
- 人物：失忆的年轻取火者，认真、好奇、直接、讲程序、自尊；不采用傲娇人格；
- 世界：同一宇宙的外星文明、漫长避难史、封闭生命系统与外部取火使命；
- `bo`：由真实睡眠、步数、站立和运动形成，可消费、可用于共同物件和返航，不可购买；
- 压力：低积累会推迟高耗能行动、使命准备和部分故事，但不伤害 Pibo 或关系；
- 主线：七阶段、二十一个核心事件完整大纲已经建立；
- 终局：双方明确选择后物理返航；地球共同生活和主线结束，App 转为低频远程连接；
- 叙事方法：固定预写主线、主页发现、主动进入、混合载体、可退出、完成后留下持续变化；
- Onboarding：新森林相遇、临时合作、健康权限、通知权限、进入正式主页的六场面结构已确认；
- Onboarding 文案规则：语言损伤、授权前身份信息和“接受临时合作”按钮已确认；
- 初版功能方向：健康记录、餐食相机、Walk Doodle、足迹、Pibo 与 `bo` 循环；
- 长期商业化、养成、社交和战斗边界已记录，但不属于 MVP 实现范围。
- PiboWorld 中的首页状态文案池已按新人物、低压力伦理、六状态和 Core 内容键完成 v1.1 叙事校正；旧编号保留作迁移检索，不适用条目已标记停用。

## MVP 建议冻结点

不需要先把一年主线写成完整剧本。进入 MVP 实现前，只需冻结：

1. 世界规则、Pibo 人物、`bo`、伦理和二十一个事件大纲；当前已完成；
2. MVP 真正出现的事件 01–03；事件基础已完成；
3. Onboarding 六场面、完整文案和状态分支；已完成并已在 iOS、HarmonyOS 实现；
4. 第一枚真实 `bo` 的触发、成熟、拔取、库存和失败边界；规则与双平台账本已实现，待真机跨日验收；
5. 新旧叙事迁移范围与 MVP 功能清单；规格和工程迁移已完成，待旧用户升级验收。

达到这一节点后应开始实现 MVP，同时继续深化事件 04 以后内容。后续故事按二十一个事件骨架逐章补充，不等待整年剧本全部完成。

## MVP 明确不做

- 付费墙、付费餐食相机、装扮商店、付费皮肤和会员增值；
- 社交、查看其他 Pibo、信号站、实时聊天和共同社群；
- 战斗、PvE、PvP、赛季和除 Walk Doodle 外的其他游戏；
- LLM/VLM 动态生成主线；
- 第一版之外的相机能力；
- 旧坠落求救、找光、命名、语音唤醒、故障逼授权和低活动伤害 Pibo。

这些能力仅保留未来架构与伦理边界，不应提前开发。

## 当前未决问题

决定 032 的“共同物件”硬解锁已经在 iOS 与 HarmonyOS 落地。解锁页完整展示名称、
图片、价格、能力与权限边界，展开时先展示「解锁后获得」，完成后以「回到森林」结束。
未拥有时对应入口不出现在主页，显示层与路由层都按 Core capability 再校验；健康授权、
原始健康归档和 `bo` 形成不受物件门控。

当前映射为：吊床开放睡眠回顾与睡醒通知，通知被拒绝时仍可从吊床查看 App 内回顾；
补梦风铃一次开放露珠相机与 Walk Doodle；状态观测仪作为森林物件打开恢复状态 Modal，
只显示「等待数据」或「正在校准」，不借用压力/Wellness 分数；铃兰灯只保留逐盏魔法
点灯。物件 capability、价格、顺序与前置均由 `pibo-core 0.10.0` 统一提供。

2026-08-07 用户再次调整并确认物件映射：补梦风铃一次解锁露珠相机与 Walk Doodle，
不增加新物件；铃兰灯不再承担 Walk Doodle，而与未来单好友 Shadow Pibo 关联。
Shadow Pibo 当前只保留概念和最小扩展接口，不进入 MVP，也不显示空壳入口。此前把
铃兰灯映射到 Walk Doodle 的 Coding Prompt 和视觉稿均已过时。

Onboarding、事件 01–03、第一枚 `bo`、双平台职责、迁移清单与验收用例已经形成 [`23-Onboarding与事件01-03跨平台MVP规格-v0.1.md`](23-Onboarding%E4%B8%8E%E4%BA%8B%E4%BB%B601-03%E8%B7%A8%E5%B9%B3%E5%8F%B0MVP%E8%A7%84%E6%A0%BC-v0.1.md)。决定 031 又收口了两个 P0 架构问题：

- `pibo-core` 是 `bo` 计分和状态转换的唯一规则源，Swift、ArkTS 和 Go 不分别复制算法；
- `bo` 本地优先形成，未登录和离线不阻塞第一枚；登录后幂等合并账本，不在 Onboarding 增加登录；
- 只把接受临时合作以后产生的健康记录用于 `bo`，此前历史只作健康展示。

`pibo-server` 的现有纯计算模型已经等价迁入 Core；当前发布版本为 `pibo-core 0.10.0`，iOS 与 HarmonyOS 均已固定到该版本。该版本同时提供 Pat V2、事件 01–03 推导、首页稳定内容键、事实过滤与共同物件 capability 映射；服务端保留 `bo v1` golden parity 测试。

双平台 MVP 基础接线已经完成：六场面 Onboarding、checkpoint 与中断恢复、旧用户迁移、故事许可、事件 01–03、Pat V2、首页稳定文案键，以及接受临时合作后才开始累计的本地 `bo` 账本均已接入。登录不阻塞启动；健康与通知权限保持独立；第一枚 `bo` 必须来自真实数据；成熟 `bo` 永不过期，也不冻结后续积累。

2026-08-06 工程 review 已补齐数据来源与迁移边界：DEBUG/Demo 健康记录和合成 workout 均有持久化 provenance，不推进事件 02、不铸造 `bo`；真实数据写入同一天时会先移除合成记录，避免未覆盖的 Demo 指标被误认成真实。账本以持久化 `firstEligibleAt` 和 `epoch:*` 日键为准，并兼容旧 `yyyy-MM-dd` 键在跨时区（含 UTC+13/+14）后的迁移。Pat 的 sleep/awake/angry 保护态不消耗普通台词预算，进入 angry 的第三次拍击也不会提前消耗普通台词。Onboarding 另存故事 checkpoint，选择“稍后”进入紧凑权限流程不会覆盖之后应恢复的身份或合作场景。iOS Home Widget 已移除旧“活力/静息/心绪”三状态展示，改为当前六状态、同步时间与新运动记录。

同日扩展发布 review 已将工程范围重新对齐决定 022/025：餐食相机与 Walk Doodle 在 iOS、HarmonyOS 都属于首发，Walk Doodle 以独立工具入口发布且不产生 `mini_game_start`，其他小游戏继续关闭。首发相机只允许“选择餐次—真实拍摄—热量识别/记录”，权限拒绝、设备不可用或拍摄失败均不得合成照片或生成餐食记录。发布配置只声明当前功能需要的健康、相机与位置权限；旧语音呼唤和小游戏动作权限不进入发布包。Widget 与运动 Live Activity 统一消费六状态 ID。Onboarding/`bo` 损坏快照按 fail-closed 与 Core 账本规则恢复，重复来源、非法书签、非有限消费和超阈值残余能量均在读取时归一化。

发布链路的进一步 review 又收口了相机生命周期、定位和历史体征语义：双端相机只在取景阶段占用硬件，快速离开/重拍时隔离过期回调并串行释放原生资源，超时或部分初始化失败不会生成餐食；iOS Walk Doodle 在仅获大概位置时不开始记录，并明确说明主动记录才使用精确位置；HarmonyOS 历史体征卡改用压力链路的 RMSSD 与 Core 个人基线分档，不再用平台 SDNN 和固定阈值把单次读数解释成“放松/紧张”。压力提醒的未来时间戳也按时间回拨 fail-open 处理。

2026-08-06 用户决定当前发布暂时关闭“临时合作”机制。iOS 与 HarmonyOS 保留六场面实现，但通过双端发布开关默认关闭，首启恢复此前的 Onboarding 页面；首页与设置不展示合作恢复入口，事件 01–03 的合作故事推进暂停。bo 不再等待“接受临时合作”，以旧 Onboarding 完成时间作为账本边界，并仍从下一个完整自然日开始计入真实健康记录。不得只隐藏按钮而留下空的 acceptedAt，否则新 bo 会停止形成。

双端工程已将“暂停”落实为持久化规则，而不只是隐藏 UI：故事健康观察与事件 03
分别保存暂停后的观察起点和 `bo` lifetime 基线，关闭期间新增的健康事实、成熟或收取
记录不会在未来重开时补推故事。`bo` 账本独立保存 `eligibilityEnabled`、
`firstEligibleAt` 和边界来源 `temporaryCooperation` / `legacyOnboarding` /
`legacyOnboardingMigration`；当前旧 Onboarding 模式继续累计。若未来重新开启临时合作，
尚未接受的用户停止新增 `bo`，但已有进度、成熟物和库存全部保留，接受后再以当时边界
继续。老版本只有 `onboardingDone` 布尔值、没有真实完成时刻时，只能以升级时刻作为
保守边界，并明确标记为 `legacyOnboardingMigration`，不得把它解释为历史精确完成时间。

当前 `PiboCoreBoDailyMetrics` 尚不能表达站立与活动消耗，并且缺失 MVPA 与实测 0 MVPA 无法区分。双端仅在 App 层排除 Core 无法表达的 source-only 日期，没有复制站立算法或阈值。完整支持必须先冻结产品数值、发布新版 Core，再依次更新 iOS exact pin 与 Harmony submodule。

当前工程未决项已经从“实现基础接线”转为真机验收：需要覆盖新用户完整流程、Onboarding 中断恢复、旧用户升级、拒绝或缺失权限、首个完整自然日跨日累计、多枚成熟待拔取，以及中英文文案和首页 SpriteKit 表现。站立、缺失/零值、行为能量、来源系数和恢复乘数不得在验收期间绕开 Core 另行解释。

叙事工作线已按决定 030 进入事件 04。现有“各取所需”仍只是关系结论，需要变成一个具体、可观察且不与事件 03 重复的事件。启动记录见 [`process/2026-07-31-Core-v0.5完成与事件04启动.md`](process/2026-07-31-Core-v0.5%E5%AE%8C%E6%88%90%E4%B8%8E%E4%BA%8B%E4%BB%B604%E5%90%AF%E5%8A%A8.md)。

## 下一步建议

1. 在 iOS 与 HarmonyOS 真机验收新用户、旧用户和中断恢复路径，确认故事许可不被健康、通知或登录状态阻塞；
2. 用真实健康数据跨过首个完整自然日，验收第一枚及多枚 `bo` 的累计、成熟、拔取、库存和幂等事件；
3. 验收首页 Pat V2、睡眠系统提示、事件 01–03、中英文稳定文案键和 SpriteKit/ArkUI 表现；
4. 叙事线继续确认事件 04 的具体行动、载体和触发间隔；
5. 不提前开发商业化、社交、战斗或其他小游戏。

共同物件还需要真机验收解锁后的森林发现、通知拒绝后的吊床回顾、相机/精确位置权限
分开请求、状态观测仪等待/校准状态，以及铃兰灯跨启动与天亮清空。Shadow Pibo 当前只有
Core eligibility 扩展点，继续禁止提前增加可见空壳入口、好友、后端、同步或隐私流程。

## 未确认功能灵感

用户提出了两个暂不对齐世界观、暂不进入 MVP 的功能灵感：单好友 [`Shadow Pibo`](ideas/2026-08-03-Shadow-Pibo%E4%B8%8E%E8%83%BD%E9%87%8F%E7%9B%91%E8%A7%86%E5%99%A8.md) 和 Pibo 可佩戴的恢复值“能量监视器”。它们只作为以后讨论的检索入口，不是已确认产品方向，也不改变当前事件 04 与 MVP 接线优先级。
