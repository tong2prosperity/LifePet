# Shadow Pibo 双向好友系统与交互提案

> 状态：产品方案已批准；正式边界见决定 043  
> 日期：2026-08-24  
> 范围：鸿蒙优先；iOS 仅记录 TODO  
> 前置：延续“只连接一位好友”和铃兰灯/好友投影的既有方向；本提案补全关系建立、双向同意、状态同步、互动闭环、隐私与退出。

## 1. 先定义它不是什么

Shadow Pibo 不是好友健康看板，也不是在线状态、聊天入口或排行榜。

用户不应该从这里知道好友走了多少步、睡了多久、何时入睡、是否完成目标，也不应该被系统暗示“你该去关心他了”。一旦把好友真实健康数据直接暴露出来，这个功能会从陪伴迅速滑向监控、比较和道德压力。

它也不能只是一张会更新的好友卡片。被动查看没有后续动作，首次新鲜感消失后，就没有继续存在的理由。

## 2. 产品内核：双方同意的远方共居

一句话定义：

> 两位用户确认连接后，彼此的 Pibo 会以“映照”形式生活在对方的森林里；映照会呈现对方 Pibo 最近同步的状态，并允许用户回一束不带文字的光。

它提供三层价值：

1. **在场感**：无需聊天、发动态或主动汇报，也能感到对方仍在远方生活。
2. **真实生活留下的变化**：用户的睡眠、活动等数据先塑造自己的 Pibo；好友看到的是变化后的 Pibo，而不是原始健康数据。
3. **无负担的回应**：用户可以表达“我看见了”，但不必组织语言，也不会形成回复义务。

这个功能真正建立的是“两只 Pibo 的远方共居关系”，好友的健康状态只是塑造投影的幕后输入，不是产品内容本身。

## 3. 核心原则

### 3.1 一位好友，而不是好友列表

- 每个账号同一时间只能建立一条有效映照关系。
- 只能有一个待处理的主动邀请；发起新邀请前必须撤销旧邀请。
- 已有关系时不能直接接受另一人的邀请，必须先主动解除当前连接。
- 不设计好友列表、搜索、推荐联系人、共同好友或关注者数量。

这不是技术限制，而是产品选择：稀缺性让这段关系有明确分量，也避免功能退化成另一个社交图谱。

### 3.2 双向同意、双向可见

- 邀请本身不建立关系。
- 接受页面必须明确说明：“接受后，你们都会在自己的森林里看到对方的 Pibo。”
- 接受后服务端以一个原子操作创建双向关系；不存在“我关注了对方，但对方看不到我”的单向状态。
- 接受前不共享任何 Pibo 状态、健康推断或历史快照。

### 3.3 分享 Pibo，不分享健康数据

好友侧只能接收共享语义状态和表现键，例如：

- `publicStateId`
- `publicBehaviorSubstateId`
- `visualVariantKey`
- `snapshotRevision`
- `occurredAt`
- `syncStatus`

不上传或分享步数、睡眠时长、心率、训练类型、卡路里、原始 HealthKit/Health Service 数据、bo 数量、历史记录或状态推断依据。

平台使用同一套 Core 语义状态映射，但通过固定的 Shadow 渲染器表现：好友看到的是“对方 Pibo 此刻的公开姿态”，不是一份健康报告。

### 3.4 状态同步不是在线状态

- 界面不显示“在线”“离线”或绿色在线点。
- `updatedAt` 只表示 Pibo 状态最后一次同步，不代表好友正在使用手机或 App。
- 不因好友状态变化默认发送通知。
- 不用“很久没来了”“对方需要你”等文案解释陈旧状态。

### 3.5 关系动作不产生资源收益

邀请、接受、查看、回光都不产生 bo、经验、连续天数或物件进度。关系不能变成刷取资源的工具，也不能因奖励设计制造回复压力。

## 4. 关系状态机

| 状态 | 用户看到什么 | 可执行动作 |
| --- | --- | --- |
| `none` | 铃兰灯的好友映照说明 | 邀请一位好友 |
| `invite_outgoing` | 等待对方确认、邀请失效时间 | 再次分享、撤销邀请 |
| `invite_incoming` | 发起人身份、双方共享说明 | 接受、暂不接受、屏蔽 |
| `active_waiting_snapshot` | 连接已建立，但对方还没有新的同意后快照 | 等待；管理关系 |
| `active_fresh` | 好友 Shadow Pibo 和新鲜状态 | 查看、回一束光、管理关系 |
| `active_cached` | 最近一次同步的 Shadow Pibo | 查看最近同步时间、回一束光 |
| `active_paused` | 最近快照继续存在，但明确“映照暂停更新” | 管理关系 |
| `ended` | 投影消失；一次性中性说明 | 重新邀请其他人 |
| `blocked` | 不显示对方，也不接收其邀请 | 在设置中解除屏蔽 |

关系状态和同步新鲜度必须分开建模。网络中断不会把 `active` 关系误判成 `ended`，陈旧快照也不会导致好友从森林里消失。

## 5. 完整用户流程

### 5.1 发现入口

入口保留在首页森林中的铃兰灯，而不是增加一个通用“好友”图标。

首次点击打开设计系统中的 half sheet：

- 标题：`让一位朋友的 Pibo 来到这里`
- 说明：`连接需要双方确认。确认后，你们都会看到对方 Pibo 最近同步的状态。`
- 主要动作：`邀请一位朋友`
- 补充说明：`不会分享步数、睡眠时长或其他健康数据。`

当前关于铃兰灯的解锁规则需要调整。**建议把基础好友连接定义为免费能力：铃兰灯承担叙事入口和投影载体，而不是接受好友邀请的 bo 门槛。** 否则邀请接收方可能先被迫完成一段养成进度，邀请转化会被产品内部条件打断，也与“基础社交免费”的既有边界冲突。该建议会修改 decision 032 的既有硬解锁定义，实施前需要单独批准。

### 5.2 发起邀请

首版只提供有意图的外部邀请：

- 系统分享链接
- 面对面二维码
- 可复制的短码作为兜底

不在首版请求通讯录权限，也不做用户名搜索。只有一位好友时，导入整个通讯录的权限成本远大于价值。

邀请规则：

- 邀请令牌单次使用，72 小时失效。
- 邀请链接只暴露邀请人的展示名称和 Pibo 静态预览，不暴露当前状态。
- 同一用户同一时间只能保留一个有效主动邀请。
- 发起者可随时撤销；撤销和过期都不向对方发送解释性通知。
- 分享文案明确双向结果，而不是模糊地说“来看看我的 Pibo”。

建议分享文案：

> 我想让我们的 Pibo 在彼此的森林里见面。接受后，我们都会看到对方 Pibo 最近同步的状态。

### 5.3 接受邀请

邀请链接打开一个独立的确认页或 half sheet：

- 发起人展示名称
- 发起人的 Pibo 静态预览，仅用于确认身份
- `这是一条双向连接`
- `你们会看到彼此 Pibo 的公开状态，不会看到健康数据`
- 主要动作：`接受连接`
- 次要动作：`暂不接受`
- 低优先级动作：`屏蔽此人`

接受时服务端必须再次检查：令牌未过期、未被使用、不是自己邀请自己、双方均未建立其他有效关系、双方未互相屏蔽。接受操作必须幂等。

如果接收方尚未安装 App，网页落地页保留邀请上下文，安装和登录后继续完成接受。不能在安装完成时自动建立关系。

### 5.4 首次显现

接受成功只建立关系，不使用接受前的旧状态偷跑投影。双方分别在下一次成功同步后生成一份“同意后快照”。

首页进入时：

1. 铃兰灯先亮起。
2. 投影从铃兰灯附近出现，使用已确定的 Shadow 渲染参数。
3. 首次只出现一次简短说明：`这是朋友的 Pibo 映照。它会保留最近一次同步的样子。`
4. 之后不再重复教学。

如果对方尚未上传同意后快照，铃兰灯保持已连接状态，half sheet 显示：`连接已经建立。等对方下一次打开 Pibo，映照就会来到这里。`

### 5.5 日常共处

- Shadow Pibo 固定在首页的次要视觉锚点，不遮挡本地 Pibo、物件和右上角相机。
- 复用现有 Pibo 状态和姿态语义，由 Shadow 渲染层统一应用颜色、透明度、轮廓、纸张颗粒和铃兰投影。
- Shadow 不说话、不被拍一拍、不使用本地物件、不获得 bo、不触发本地健康动作，也不抢占本地 Pibo 的主角位置。
- 点击 Shadow 只打开好友状态 half sheet。

当前已确定的渲染参数：

```json
{
  "schemaVersion": 1,
  "semanticRole": "friend_shadow_projection",
  "bodyColor": "#E5E5F5",
  "opacity": 0.75,
  "outline": {
    "widthPx": 5,
    "color": "#23BE94"
  },
  "paperGrain": 0.09,
  "lilyProjection": 0.32
}
```

### 5.6 好友状态 half sheet

信息层级保持克制：

1. 好友展示名称 + 小型 Shadow Pibo
2. 一句公开状态描述，例如 `今天看起来很有精神`
3. 新鲜度：`刚刚同步`、`18 分钟前同步`、`最近一次 · 昨天 22:14`
4. 主要动作：`回一束光`
5. 低优先级入口：`管理连接`

不展示健康数值、趋势图、状态原因、设备在线情况或“建议你联系好友”。

## 6. 必须存在的最小互动闭环：回一束光

纯被动投影只能完成“看见”，不能建立关系闭环。首个可发布版本应保留一个且仅一个社交动作：

> 用户看到好友的 Pibo 后，可以“回一束光”；对方的铃兰灯在下一次可展示时短暂亮起，表达“我看见你了”。

行为边界：

- 不允许输入文字、表情或预设评价。
- 不根据对方 Pibo 状态改变含义；它不是“安慰”“催促”或健康建议。
- 不显示未读数、连续回应天数、谁欠谁一次回复。
- 不产生奖励，也不要求对方回光。
- 多次快速操作在服务端合并，不让接收方连续播放。
- 离线时保留最近一束未呈现的光；24 小时后自然失效，不堆积历史队列。
- 展示只复用铃兰灯的光效和轻量粒子，不要求新增 Pibo 动作资源。

建议接收侧只出现：铃兰灯短暂变亮 + `远方来了一束光`。不弹出模态框，不打断当前操作。

这一步把产品闭环从：

`连接 → 看见`  

变成：

`连接 → 看见变化 → 轻量回应 → 对方感到被看见`

## 7. 同步模型

### 7.1 触发时机

状态快照采用事件驱动，而不是高频轮询：

- Core 公开语义状态发生变化
- 公开表现键发生变化
- App 回到前台并发现本地快照较旧
- 关系建立、恢复同步或账号切换
- 后台系统允许时进行低频补发

目标体验：

- 双方都在前台且网络正常：状态变化后约 10 秒内可见。
- 一方在后台：系统能力允许时尽快更新，不承诺“在线直播”。
- 接收方冷启动或回到前台：立即拉取最新快照。
- 无网络或请求失败：继续展示本地缓存的最近有效快照。

### 7.2 新鲜度

| 新鲜度 | 展示策略 |
| --- | --- |
| 15 分钟内 | `刚刚同步` 或 `X 分钟前同步` |
| 15 分钟至 24 小时 | 展示当天时间 |
| 超过 24 小时 | 明确标注 `最近一次` 和日期时间 |
| 暂停同步 | 保留最近一次快照，标注 `映照暂停更新` |

状态陈旧不会让 Shadow 变灰、受伤或消失，也不会触发提醒。时间信息负责诚实表达数据新鲜度，视觉不负责惩罚好友缺席。

### 7.3 冲突和回退

- 每个用户的快照使用单调递增 `snapshotRevision`。
- 服务端和客户端只接受更高 revision；同 revision 时以服务端确认时间去重，不以网络到达顺序覆盖。
- 渲染失败时保留上一份可渲染快照，并记录不可识别的 `visualVariantKey`。
- Core/客户端版本不兼容时回退到对应公开状态的基础姿态，不回退成 `stable`，也不让 Shadow 消失。
- `dataUnknown` 不作为新的好友公开状态发送；数据暂不可用时保留最近一次有效公开快照，并更新同步状态。

## 8. 隐私、暂停、解除和屏蔽

好友 half sheet 的 `管理连接` 提供：

### 8.1 同步我的 Pibo 状态

- 默认开启。
- 关闭后停止上传新快照；好友继续看到最近一次快照，并看到 `映照暂停更新`。
- 暂停不影响用户查看好友主动分享的状态。隐私控制不以对等交换为条件。

### 8.2 在首页显示好友映照

- 默认开启。
- 关闭只影响本地显示，不会改变自己的分享状态，也不会通知好友。

### 8.3 解除连接

- 明确确认：解除后双方都会失去彼此的映照。
- 服务端立即撤销双向关系并删除双方可共享的最新快照。
- 对方下次打开时只看到一次中性信息：`这段映照连接已经结束。`
- 不解释是谁解除、为什么解除，也不使用失落、责备或挽留文案。

### 8.4 屏蔽

- 立即解除连接、撤销待处理邀请，并阻止双方再次互发邀请。
- 被屏蔽者不收到“你被屏蔽”的通知。
- 屏蔽列表只在账号隐私设置中管理。

## 9. 异常和边界状态

| 场景 | 处理 |
| --- | --- |
| 邀请过期或已使用 | 显示 `这个邀请已经失效`，允许发起人生成新邀请 |
| 接收方已有好友 | 不允许就地替换；引导其先管理现有连接 |
| 发起方在接受前建立了其他关系 | 接受失败，显示中性失效提示 |
| 自己打开自己的邀请 | 不允许接受，回到当前连接页 |
| 一方卸载 App 或长期离线 | 保留最近一次快照和真实同步时间，不推断关系结束 |
| 一方退出账号 | 本地 Shadow 缓存按账号隔离；不把上一账号好友显示给新账号 |
| 服务端不可达 | 使用缓存；不把“网络失败”说成“好友离线” |
| 一方暂停同步 | 保留最后快照，显示暂停，不推断原因 |
| 一方解除或屏蔽 | 双方投影移除；本地缓存不可继续恢复 |
| Shadow 资源缺失 | 使用基础 Shadow 姿态和统一渲染参数 |

## 10. 首版页面/状态清单

视觉设计阶段至少需要覆盖以下 9 个状态，不应只画“好友已经出现”的理想态：

1. 空状态：铃兰灯好友映照 half sheet
2. 生成邀请：分享链接/二维码
3. 等待确认：邀请进行中
4. 收到邀请：双向同意页
5. 已连接、等待对方首个快照
6. 首页首次显现
7. 首页稳定共处
8. 好友状态 half sheet + 回一束光
9. 缓存/暂停/解除等管理状态

视觉规则沿用已经确定的 sheet 设计系统；Shadow 本体沿用当前 `rendering-spec.json`。不再用生图重新发明历史页、相机页或其他现有 UI。

## 11. 服务端最小数据合同

建议实体：

- `shadow_invitation`
  - `id`, `inviterUserId`, `tokenHash`, `expiresAt`, `status`, `createdAt`
- `shadow_relationship`
  - `id`, `userAId`, `userBId`, `status`, `acceptedAt`, `endedAt`
- `shadow_snapshot`
  - `relationshipId`, `ownerUserId`, `publicStateId`, `publicBehaviorSubstateId`, `visualVariantKey`, `revision`, `occurredAt`, `receivedAt`, `sharingStatus`
- `shadow_light_signal`
  - `relationshipId`, `senderUserId`, `createdAt`, `expiresAt`, `consumedAt`
- `shadow_block`
  - `blockerUserId`, `blockedUserId`, `createdAt`

所有接口按当前登录账号验证关系，不接受客户端传入任意好友 ID 获取快照。服务端只返回与当前有效关系相关的对方公开快照。

## 12. 成功指标和护栏

北极星不是邀请数量，而是关系是否持续产生双向在场感。

建议首版核心指标：

> 新建立的映照关系中，7 天内双方都在至少 3 个不同日期看见过对方有效 Shadow 快照的关系占比。

辅助指标：

- 邀请打开率、接受率、接受耗时
- 双方首个快照到达率和耗时
- Shadow 点击率
- 回光发送率、接收侧实际呈现率
- 快照陈旧比例、同步失败率
- 暂停分享率、解除率、屏蔽率

护栏：

- 不以高通知打开率优化产品
- 不把回光次数或连续天数展示给用户
- 单用户邀请生成频率和失败尝试需要风控
- 屏蔽、解除和暂停必须比建立关系更容易找到

## 13. MVP 范围

### 必须实现

- 单好友限制
- 外部链接/二维码邀请
- 双向同意和幂等关系建立
- 同意后首个快照
- 公开语义状态近实时同步
- 最近一次有效快照回退
- 首页 Shadow 统一渲染
- 状态 half sheet
- 回一束光
- 暂停分享、隐藏本地投影、解除、屏蔽
- 邀请/关系/同步异常状态
- 鸿蒙端完整闭环

### 明确不做

- 多好友列表和好友推荐
- 通讯录上传、附近的人、共同好友
- 文字聊天、语音、图片、表情
- 健康数据、步数、睡眠时长和趋势共享
- 好友健康提醒或 AI 关心建议
- 排名、打卡、连续天数、资源奖励
- 访问好友完整森林、赠送物件或转移 bo
- 实时位置、在线状态和最后活跃时间

## 14. 已批准的四个决定

2026-08-24 用户确认：

1. **单好友是长期原则，不是首版临时限制。**
2. **基础好友连接从铃兰灯的 bo 硬解锁中移出。** 免费开放连接能力，铃兰灯承担入口和世界观载体。
3. **“回一束光”进入首版。** 没有它，Shadow 更像状态组件而不是关系产品。
4. **暂停分享后仍可查看对方主动分享的状态。** 隐私不作为强制交换，但界面必须诚实显示自己的映照已暂停。
