# `pibo-server` 现有 `bo` 算法复核

> 日期：2026-07-30  
> 状态：代码复核结论；替代 24 号文档中“先简化算法”的倾向  
> 范围：只描述现有实现、接线缺口和迁移影响，不在本文修改数值规则。

## 1. 结论

`pibo-server` 已经存在一套完整且有明确设计依据的 `bo` 经济系统，不是简单的阈值占位逻辑。它包含：

- 原始健康样本持久化；
- 请求级和样本级两层幂等；
- 按服务端固定时区进行每日聚合；
- 睡眠多维评分；
- 步数、MVPA、恢复状态和数据来源曲线；
- 健康能量每日目标与差额发放；
- App 行为能量的独立上限；
- 跨日能量池、整数 `bo` 铸造、头顶待拔数量与流水；
- 动画语义和 Pibo 六状态派生。

因此，迁入 `pibo-core` 时应把现有服务端算法作为主要基线进行等价迁移和产品冲突审计，不能只因为客户端尚未上报完整输入，就先把曲线系统改写成简单线性累加。

## 2. 真实执行链路

一次 `/api/v1/economy/sync` 在单个数据库事务中依次执行：

1. 使用 `(user_id, idempotency_key)` 领取请求幂等键；重复请求直接返回此前保存的完整响应；
2. 获取或创建用户 Economy 账户；
3. 按 `(user_id, dedup_key)` 插入新的健康样本；
4. 按 `(user_id, event_id)` 插入新的 App 行为；
5. 依据服务端固定时区处理每日预算切换；
6. 查询当天已经持久化的各项健康指标总量；
7. 将总量映射成 `DailyMetrics`，调用 `ScoreDay`；
8. 只发放 `max(0, 当日新目标 - 当日已经发放)`，已经发出的能量永不回收；
9. App 行为能量另外按每日上限发放；
10. 把新增能量加入跨日 `EnergyPool`，每跨过 `EnergyPerBo` 铸造一枚 `bo`；
11. 每枚新 `bo` 增加 `BoPending` 并写入 append-only `bo_ledger`；
12. 保存账户，返回 `bo_pending`、`bo_balance`、剩余能量、铸造结果、状态和动画语义；
13. 保存完整响应，供相同幂等键重放。

这套设计的重点不是“每条样本加多少”，而是先得到一天的完整状态，再计算这一天应当达到的目标，并只补足差额。

## 3. 已实现的复杂评分

### 3.1 每日总公式

```text
base = 睡眠分 × 0.45 + 步数分 × 0.30 + MVPA 分 × 0.25
raw = base × 100 × 恢复乘数 × 数据源系数
dailyEnergy = min(110, raw)
每累计 75 energy 铸造一枚 bo
```

数值来自 `DefaultConfig()`，具体参数属于可调层，不因本文复核而重新拍板。

### 3.2 睡眠不是只看时长

服务端的 `ScoreSleep` 包括：

- 实际睡眠时长 TST 的非对称曲线；
- 睡眠效率；
- 五分钟以上夜醒次数；
- 入睡潜伏期；
- 深睡和 REM 的小额正向 bonus；
- 缺失质量数据时按中性降级，而不是按零分处罚。

现有测试明确覆盖正常睡眠、长睡回落和碎片睡眠差异。

### 3.3 其他曲线

- 步数：单调上升后饱和，超过约 10,000 步不再增加，也不扣分；
- MVPA：45–60 分钟附近达到峰值，极长运动软回落；
- 恢复：HRV/静息心率派生的 0–4 等级映射为约 `0.85–1.10`；缺失时使用中性值；
- 数据来源：预留 watch `1.0`、phone `0.8`、app `0.55`；
- App 行为：photo `5`、game `8`、pat `0`，每日合计最多 `10`。

上述曲线均有配套设计文档和文献说明。是否与当前新叙事完全兼容，需要逐项讨论，但不能在未讨论前视为无意义旧代码。

## 4. 服务端已经预留的经济状态

`EconomyAccount` 已有：

- `EnergyPool`：距离下一枚 `bo` 的剩余能量；
- `EnergyToday`：当天已经发放的健康能量；
- `ActionEnergyToday`：当天已经发放的行为能量；
- `BoPending`：头顶已成熟、尚未拔取的 `bo` 数量；
- `BoBalance`：拔取后可消费库存；
- `LastPluckAt`：最后拔取时间；
- `LastSyncAt`：最后同步时间。

`BoLedger` 也预留了 mint、pluck、spend_item、decay 等原因。

但当前仍是“切片 1”：铸造、待拔数量和 mint 流水已经实现，真正的 `BoPending → BoBalance` 拔取事务和消费接口尚未实现。不能只看字段存在就认为事件 03 已完成。

## 5. 算法完整与产品接线不完整同时成立

当前 iOS/HarmonyOS 的 Economy 同步只上传步数和睡眠总时长。服务端支持但客户端尚未完整上报：

- `mvpa`；
- `sleep_in_bed`；
- `sleep_deep`；
- `sleep_rem`；
- `sleep_latency`；
- `sleep_awakenings`；
- `recovery`；
- `DailyMetrics.Source` 所需的来源分类。

本地健康历史中已经存在活动消耗、运动分钟、站立、睡眠分期和部分心率数据，因此主要问题是 Economy DTO 和映射没有接齐，而不是服务端完全没有计算逻辑。

站立是新故事已经确认的 `bo` 来源，但现有服务端公式没有站立指标。这是需要新增或重新映射的真实产品差异。

## 6. 代码复核发现的具体边界

### 6.1 “缺失运动”与“运动为零”目前不可区分

`DailyMetrics.MVPAMinutes` 是非可选数值。聚合中没有 `mvpa` 时会得到 0，而现有 MVPA 曲线在 0 分钟处返回 0.2。因此没有上报运动指标时，运动柱仍贡献 `0.2 × 0.25 × 100 = 5` 点中性能量。

这可能是设计者刻意避免“无运动即惩罚”，也可能会与“完全没有真实数据就不形成 `bo`”冲突。迁入 Core 时需要显式区分：

- 数据缺失；
- 有记录且当天为零；
- 有记录且大于零。

是否保留零运动的基础分，需要产品拍板，不能由数据类型偶然决定。

### 6.2 数据来源系数实际上尚未生效

`DailyMetrics.Source` 虽有字段和单元测试，但 `assembleDailyMetrics` 没有给它赋值，客户端 DTO 也没有上报该分类。当前线上式计算通常落到缺省 `1.0`。

所以 watch/phone/app 系数目前是已实现的纯规则和测试能力，不是完整接线后的真实产品行为。

### 6.3 睡眠归属存在跨日风险

服务端按样本 `start_ts` 所在的服务端日聚合。客户端健康历史把昨晚睡眠归到今天的“醒来日”，但上传样本仍使用实际 `sleepStart`。例如昨晚 23:00 开始、今天 07:00 结束的睡眠，在今天调用 sync 时可能被归到昨天；而当前 Sync 只重算“今天”。

现有端到端测试把睡眠样本人为放在当天中午，未覆盖真实跨午夜睡眠。这一归属问题必须在迁移 Core 或修服务端前增加测试。

### 6.4 历史补录不会重算所属日

当前 Sync 只重算服务器“今天”。晚到的历史睡眠或活动样本即使成功持久化，也不会自动重算其所属历史日的目标。现有文档已经把它标为后续切片，但它会影响长期积累准确性。

### 6.5 App 行为能量与新叙事冲突

现有 photo/game 行为能量是刻意设计的“无完整健康数据用户兜底”，不是偶然代码。但新叙事决定 003/016 已明确 `bo` 只能由真实健康行为形成，拍照和游戏不得自动成为健康能量。

这里需要明确迁移：可以保留行为流水用于其他养成或功能奖励，但不能继续进入同一个 `bo` 铸造池，除非未来正式推翻现有叙事决定。

### 6.6 匿名身份能力存在但客户端未接

服务端 identity 已支持：

- `POST /auth/device`：使用 installation ID 换取匿名账号；
- 手机号验证码登录时携带 installation ID：把匿名账号原地升级，用户 ID 不变，既有数据不丢。

当前 iOS/HarmonyOS Economy 客户端只实现显式手机号登录，没有使用匿名设备身份。因此未登录 `bo` 有至少两条可行路径：

1. 决定 031 已确认的本地 Core 优先，之后幂等合并；
2. 客户端无感建立匿名后端账号，服务器继续权威运行同一 Core。

两者并非互斥：本地 Core 可以保证离线体验，匿名账号可以尽早提供云端账本与恢复。实现时应评估是否组合，而不是误以为服务端一定要求用户先看见登录页。

## 7. 测试状态

已验证：

- `go test ./internal/economy/service/...` 通过；
- 曲线插值、睡眠评分、每日评分、恢复系数、来源系数、能量铸造、每日上限和状态派生均有纯函数测试；
- 仓库存在真实 HTTP + PostgreSQL 的 Economy 端到端测试，覆盖登录、铸造、请求重放、样本去重、state 和 config。

当前问题：

- `go test ./internal/economy/...` 在集成测试编译阶段失败；
- 原因是 identity 依赖的日志参数已从旧 logger 类型变为 `*slog.Logger`，测试装配仍传旧类型；
- 这不是数值断言失败，但意味着当前完整 Economy 测试并非绿色，需要先修测试装配才能重新验证端到端行为。

## 8. 对 `pibo-core` 迁移的修正建议

正确顺序应是：

1. 把服务端现有纯函数、配置、fixture 和设计依据视为迁移基线；
2. 先为当前 Go 算法补齐缺失/零值、跨日睡眠、历史补录和站立来源测试；
3. 将已确认保留的算法等价迁入 Rust `pibo-core`；
4. 用同一批 golden fixture 对比 Go 与 Rust 结果，确保迁移期间不静默改数值；
5. 对与新叙事有冲突的部分——行为能量、缺失运动基础分、站立缺失、设备系数和负向恢复——逐项拍板；
6. 决定是否保留 Go 逻辑作为短期对照，最终由同一 Core 产物消除双规则源；
7. 再接齐 iOS、HarmonyOS 和匿名身份/本地账本链路。

## 9. 本轮不再提前假定的结论

24 号文档提出了“统一改为单调封顶、取消设备系数、取消 HRV 影响”等方向。这些尚未获得用户确认，而且是在未完整复核服务端实现前提出的。

本复核撤回把它们当作默认下一步的倾向。后续讨论应以现有复杂模型为基线，逐项判断哪些符合新的 Pibo 叙事与健康观，哪些只是接线问题，哪些确实需要调整。
