# `bo` 数值审计与 Core v0.1 方向提案

> 日期：2026-07-30  
> 状态：已被 [`25-pibo-server现有bo算法复核.md`](25-pibo-server%E7%8E%B0%E6%9C%89bo%E7%AE%97%E6%B3%95%E5%A4%8D%E6%A0%B8.md) 修正；N1–N3 不再作为默认待确认项  
> 范围：判断当前后端数值能否迁入 `pibo-core`，先确定体验目标与结构，不在本文件直接拍板最终断点。

## 1. 为什么现在不能直接采用 `75/110`

> 修正说明：进一步完整复核 `pibo-server` 后确认，现有实现是一套有设计文档、文献依据、纯函数测试和端到端测试骨架的复杂经济模型，应作为迁入 `pibo-core` 的主要基线。本文件后半部分提出的简化方向形成于复核不完整时，仅保留为过程记录，不应据此直接删除倒 U 曲线、恢复乘数或设备系数。当前结论以 25 号复核为准。

当前后端的设计公式是：

```text
每日健康能量 = min(110, (
  睡眠分 × 0.45
  + 步数分 × 0.30
  + MVPA 分 × 0.25
) × 100 × 恢复乘数 × 数据源系数)

每累计 75 能量形成一枚 bo。
```

这个模型有完整曲线和测试，但“公式存在”不等于“当前 App 真的提供了这些输入”。直接把它搬进 Core，会把历史工程缺口误当作新产品决定。

## 2. 当前端到端真实能力

### 已经落入健康历史

iOS 与 HarmonyOS 的健康历史目前都能保存：

- 步数；
- 睡眠总时长及部分睡眠分期；
- 活动消耗；
- 运动分钟；
- 站立分钟；
- 心率、静息心率、HRV 等部分身体信号。

### 当前真正上传到 Economy 的数据

两端 `EconomySyncCoordinator` 目前只上传：

- 步数；
- 睡眠总时长。

以下数据虽然部分已在本地历史中存在，却没有进入当前 `bo` 计算：

- 站立分钟；
- 活动消耗；
- 运动分钟/MVPA；
- 深睡、REM、清醒片段和睡眠质量；
- HRV/静息心率恢复等级；
- 可用于区分手机与手表的数据来源信息。

此外，后端 `DailyMetrics.Source` 当前没有接线，实际计算通常使用默认系数 `1.0`，而不是文档预期的 phone `0.8` 或 watch `1.0`。

## 4. 已发现的结构问题

### 4.1 无记录也可能积累

MVPA 曲线把 0 分钟映射为 0.2。由于输入模型不能区分“明确记录为零”和“根本没有数据”，缺失运动记录也会每天贡献 5 能量。

这违反“`bo` 只能由真实健康行为形成”。Core 输入必须用可选值或来源集合表达缺失；没有真实记录的维度贡献必须为零。

### 4.2 数据源系数会重复惩罚无手表用户

无手表用户本来就缺少睡眠、HRV、站立或运动等来源，能够贡献的维度已经更少。如果再把整日结果乘 `0.8/0.55`，同样一条真实步数记录会因为设备较少再次打折。

这与“没有手表也能靠步数缓慢前进”的方向存在张力，也会把购买设备变成隐性的产出加速器。

### 4.3 恢复乘数可能惩罚压力与身体状态

当前 HRV/静息心率恢复等级最低会让全日能量乘 0.85。用户处在压力、疾病恢复或睡眠不足状态时，恰好更需要被看见，却会得到更少 `bo`。

HRV 可以继续用于健康趋势和 Pibo 的观察，但 MVP 不适合用它扣减已经发生的睡眠、步行和站立贡献。

### 4.4 倒 U 曲线容易把健康 App 变成裁判

- 睡眠在 7.5–8 小时达到峰值，11 小时只剩 0.12；
- 运动在 45–60 分钟达到峰值，之后逐渐回落。

这些曲线适合做研究型健康评分，但 `bo` 的职责是把用户真实照顾身体的过程外显。长睡可能来自补觉、疾病恢复、年龄差异或设备误差；长时间运动也不应在货币层被解释为“更差”。

MVP 更稳妥的方式是单调增加后封顶：达到足够范围后不再增加，但不倒扣、不回落。健康风险由独立健康说明表达，不通过减少 `bo` 暗示惩罚。

### 4.5 已确认来源尚未全部进入模型

故事已经确认睡眠、步行、站立和运动等健康行为都能形成 `bo`。当前模型没有站立柱，端上也没有上传现成的站立与活动数据。

Core v0.1 至少需要：

- 睡眠时长；
- 步数；
- 站立分钟；
- 运动分钟或活动消耗中的一种稳定主输入；
- 明确的缺失标记与样本来源。

活动消耗、步数和运动分钟高度相关，不能三项无脑相加。建议优先使用运动分钟，活动消耗只在运动分钟缺失时作为降级输入，避免同一行为重复计分。

## 5. 建议的 Core v0.1 结构

### 5.1 四类真实贡献

```text
睡眠贡献 + 步数贡献 + 站立贡献 + 运动贡献
```

- 每类只有观察到真实记录才参与；
- 每类从零单调增长，到合理上限后保持不变；
- 不因过多而产生负值或回落；
- 每日总贡献封顶；
- 跨日累计，达到统一阈值形成一枚实体 `bo`；
- HRV、静息心率和睡眠分期暂不扣减基础贡献。

### 5.2 建议权重方向

不先冻结精确断点，先确定相对优先级：

1. 睡眠最高，保证“不运动但正常睡眠”的用户仍能稳定前进；
2. 步数第二，保证无手表用户有可靠通路；
3. 站立提供较小但真实的日常贡献；
4. 运动提供额外贡献，但不是形成 `bo` 的必要条件。

可用于下一轮 fixture 的初始比例是 `45 / 30 / 10 / 15`。这只是校准起点，不是本轮拍板数值。

### 5.3 不使用设备惩罚系数

- 不再按 watch/phone/app 对同一条真实健康记录整体打折；
- 有更多传感器只意味着能观察到更多真实维度，不改变同类记录本身的价值；
- Demo、自评、拍照、游戏和付费不属于健康记录，仍然不能生成 `bo`。

### 5.4 HRV 的 MVP 位置

- HRV 和静息心率继续服务健康趋势、状态和提醒；
- 不作为负向乘数；
- 后续若要进入 `bo`，只能先研究“正向小额补充、缺失不罚”的方案，并另行拍板。

## 6. 第一枚 `bo` 的建议体验目标

第一枚既是经济系统第一次反馈，也是事件 03。它不能授权后立即出现，也不应让普通用户等一两周才理解机制。

建议先确定时间目标，再倒推阈值：

| 用户情况 | 建议第一枚时间 |
|---|---|
| 正常睡眠 + 普通步行 | 2–3 个自然日 |
| 睡眠较好 + 活动较多 | 最快 1–2 个自然日 |
| 只有手机步数，约 3,000–5,000 步/日 | 4–7 个自然日 |
| 数据很少但每天有少量真实步数/站立 | 可以更慢，但持续前进 |
| 完全没有任何合格健康记录 | 不形成，不用虚假兜底 |

“最快 1 天”仍要求接受合作后真实记录自然发生，不是授权完成动画，也不使用接受以前的历史数据。

第一枚不建议采用单独优惠阈值。`bo` 是同一种资源，第一枚和后续使用相同规则；通过整体阈值校准体验，避免教学特例破坏用户理解。

## 7. 与长期一年主线的关系

`bo` 形成频率和故事推进频率必须分开：

- 用户可以持续形成和消费 `bo`；
- 故事使用 `lifetimeMinted/lifetimeCollected`、自然使用周期和事件前置条件共同门控；
- 即使健康活跃用户接近每天形成一枚，也不能一天连续播放多个核心事件；
- 因此不需要为了把故事拖到一年而故意让第一枚 `bo` 极慢。

## 8. 本批待确认

### N1：曲线含义

Core v0.1 不沿用睡眠和运动的倒 U 回落，改为“真实记录单调增加，到上限后不再增加”，避免 `bo` 成为健康裁判。

### N2：设备与 HRV

取消 phone/watch 的整体产出系数；HRV 和静息心率 MVP 只用于健康趋势，不扣减 `bo`。无手表用户自然依靠自己实际拥有的步数等来源前进。

### N3：第一枚时间目标

以“普通用户 2–3 天、仅手机步数用户 4–7 天、完全无记录不形成”为校准目标，再生成精确曲线、阈值和跨平台 fixture。

三项确认后，下一步才确定 Core v0.1 的精确输入结构、断点、阈值和账本合并协议。
