# 决定 031：`bo` 本地优先与 Core 单一规则源

> 决定日期：2026-07-30  
> 状态：已拍板

## 当前实现事实

当前 `bo` 经济计算主要在 `pibo-server` 执行。iOS 与 HarmonyOS 上传健康样本，后端计算能量、铸造 `bo` 并返回 `boPending`、库存和动画语义。现有同步在用户未登录时不会工作。

这与已经确认的产品流程存在冲突：六屏 Onboarding 不包含强制登录，第一枚 `bo` 又必须由真实健康数据自然形成，不能依赖用户后来偶然进入登录流程。

## 已确认方案

### 1. MVP 本地优先

- iOS 与 HarmonyOS 在设备本地根据真实健康数据形成 `bo`；
- 未登录、暂时离线或后端不可用时，第一枚 `bo` 和日常积累仍能正常工作；
- 登录后再上传本地的原始健康记录、领域事件和账本记录进行合并；
- 不在已确认的 Onboarding 中增加登录场面，也不以登录阻塞事件 03。

### 2. `pibo-core` 是唯一确定性规则源

- 健康数据聚合、来源资格、曲线、阈值、单日封顶、进位、状态转换、去重语义和领域事件键统一实现在 Rust `pibo-core`；
- iOS 和 HarmonyOS 分别调用同一 Core 发布版本，不在 Swift 或 ArkTS 中复制算法；
- 现有后端 Go 计分实现作为迁移来源接受审计，但不继续成为与 Core 并行演化的第二套规则；
- 具体初始阈值和曲线仍需在 Core 迁移时通过 fixture 验证，不能仅因后端当前使用某个数值就自动视为新的产品决定。

### 3. 后端分阶段职责

MVP 阶段：

- 后端负责账号、上传、稳定 ID 去重、账本保存、合并和跨设备镜像；
- 后端不使用另一套 Go 算法重新决定客户端是否应当形成 `bo`；
- 当前没有付费购买 `bo`、社交竞争或战斗排名，MVP 可以先接受本地 Core 结果，并保留原始输入与规则版本用于审计。

未来需要防作弊、付费资产或跨用户竞争时：

- 后端必须运行同一份 `pibo-core` 产物或由它生成的确定性验证产物进行复算；
- 可以选择 Rust 库绑定、WASM 或独立 Core 执行服务，但不得在 Go 中手工维护另一套曲线和阈值；
- 客户端与后端结果冲突时，以同一 Core 版本对原始输入重新计算并对账。

因此，算法只编写和维护一次。增加的是平台数据适配、持久化和同步职责，而不是第二套业务算法。

### 4. 故事许可时间边界

- 用户点击“接受临时合作”时记录 `acceptedAt` 和许可版本；
- 只有结束时间不早于 `acceptedAt` 的合格健康记录可以形成 `bo`；
- 接受合作以前的健康历史仍可用于健康记录展示，但不追溯转换为 `bo`；
- 这保证平台健康授权和 Pibo 故事许可真正分离，也避免在用户同意以前替 Pibo 使用历史数据。

## 对现有工程的影响

- 先把经过审计的健康计分与 `bo` 状态转换迁入 `pibo-core`，补齐跨平台 fixture 并发布 SemVer；
- iOS/HarmonyOS 增加本地 `bo` 账本、待同步队列和规则版本；
- 后端现有计分路径停止作为新规则源，转为账本合并与未来同 Core 复算的迁移基础；
- 上传必须携带稳定记录 ID、领域事件 ID、`scoringVersion` 和故事许可时间边界；
- 登录合并必须幂等，不能把本地已经形成的 `bo` 再铸造一次。

## 它否定了什么

- 否定“未登录就无法形成第一枚 `bo`”；
- 否定为了使用后端经济系统而在 Onboarding 中增加强制登录；
- 否定 Swift、ArkTS 和 Go 各自复制一份计分算法；
- 否定把接受临时合作以前的健康历史追溯转换为 `bo`。

## 仍未决定

- Core 首版具体曲线、阈值和单日上限；
- 本地账本与账号已有远端账本发生冲突时的详细合并协议；
- 后端未来采用 Rust 绑定、WASM 还是独立执行服务运行同一 Core；
- 这些属于实现与数值规格，不改变本决定的单一规则源和本地优先方向。
