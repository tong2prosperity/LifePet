# 决定 033：Pibo 情境闲聊与拍一拍调度机制

> 决定日期：2026-08-19
>
> 状态：已冻结机制；六个 Core 主状态的首版内容与行为边界均已审核通过
>
> 实现顺序：先 HarmonyOS，iOS 标记 TODO，未重新授权前不同步修改

## 决定内容

Pibo 的“拍一拍”不再是随机台词、概率开口或有每日次数上限的奖励按钮。它是用户向
Pibo 发起的一次接触，Pibo 在当前 Core 主状态、行为子状态、事件原因、实时事实和
故事阶段下给出简短回应。

这一机制定义为“状态驱动的情境短句系统”，不是对话树、随机台词库或运行时生成式
聊天机器人。用户的真实健康事实决定 Core 主状态；拍一拍只呈现 Pibo 对该事实的
理解、判断和当下意图，不能伪造健康恢复。

## 公开参考与取舍

公开资料没有披露任天堂的内部数据结构，以下是从开发者公开说明中提取的产品机制，
不宣称是对任天堂内部工具链的还原。

- 《超级马里奥兄弟：惊奇》曾用约六个月尝试跟随玩家动作的实时解说，但泛化播报员缺少
  世界内身份，多人格语音变体又带来巨大工作量。最终解说被改造为花花王国中真实存在的
  “闲聊花花”，在恰当时机补充提示、共鸣和陪伴感。Pibo 已经是森林中的说话者，无需再增加
  旁白设备或第二角色。

  参考：<https://www.nintendo.com/au/news-and-articles/ask-the-developer-vol-11-super-mario-bros-wonder-chapter-3/>
- 《动物森友会》把角色行为与对白视为同一序列设计职责。Pibo 也必须先有状态、子状态和当下
  行为，再写与其一致的文案，不先写一堆“可爱的话”再随机播放。

  参考：<https://iwataasks.nintendo.com/interviews/wii/accf/0/0/>
- 《Hades》的对白依赖事件资格、顺序和优先级，关键新事件不应被普通闲聊压住。Pibo 只借鉴
  “有意义的新情境先回应一次”，不复制其海量分支规模。

  参考：<https://www.gdcvault.com/play/1026975/Breathing-Life-into-Greek-Myth>、<https://www.supergiantgames.com/blog/hades-updates/>
- 《Bastion》的即时旁白强调简短和潜台词：不重述玩家已经看见的事，而是增加角色意图、世界细节或
  关系信息。Pibo 接受这一原则，但不采用《Bastion》的绝对不重复规则；Pibo 是长期日常产品，
  允许顺序循环。

  参考：<https://www.supergiantgames.com/blog/in-depth-writing-bastion/>

## 情境解析与选句

1. 用户点击 Pibo，若正在冷却期则直接忽略。
2. 接受本次点击时，读取 Core 主状态、子状态／原因、当前可用事实和故事阶段。
3. 若当前已有尚未说完的微章节，且 Core 主状态没有改变，本次有效点击优先推进它的下一句。
4. 否则若存在尚未回应的新状态或新事件，下一次有效点击先进入对应事件情境池一次；它不主动
   弹出气泡。
5. 否则进入当前 `state + context` 普通情境池。
6. 每个池只有一个记录游标；从游标开始循环扫描，跳过实时变量缺失或故事阶段不满足的互动单元。
7. 成功选取后显示该单元的第一句；若它只有一句则完成后移动记录游标，若有多句则保留当前
   微章节位置，待后续有效点击推进。
8. 到达池尾后从头循环。不使用随机数、权重或文案 ID 判断重复。记录游标建议按
   `state + context` 持久化，内容版本更新时才安全重置。

## 文案源与最小字段

同一种状态的文案和对应语义动作集中在一个大的 JSONL 著作源中，不再拆成大量小文件。
首期每条记录仅保留：

- `state`：Core 主状态。
- `context`：该主状态下的子状态、原因或事件情境。
- `action`：跨端稳定的语义动作；缺少专门动画时可使用当前回退，不阻塞文字互动。
- `speaker`：说话者语义；Pibo 的台词与系统错误说明不混用。
- `lines`：一个完整互动单元内按点击顺序出现的句子；只有一句时就是普通单句，多句时就是微章节。
- `text`：该次点击显示的简体中文文字；当前版本不是多语言字典。
- `stages`：可选，限制该句可以出现的故事阶段。

不增加手工 `id`、随机权重、每日上限、单句冷却、动画资源名或情绪人格标签。说话触发、
冷却、情境解析和确定性选择属于共享 Core 规则；平台只负责装载、展示、本地持久化和可选的
动画／触觉效果。具体代码边界在 HarmonyOS 实现前再按 Core 的发布顺序落地，本决定不授权双端
各自复制一套选句算法。

同一 `state + context` 可以写多条 JSONL 记录，每条记录代表一个完整互动单元；记录之间按游标
循环，记录内部按 `lines` 顺序推进。因此无需增加 `mode` 字段：单句与微章节只由 `lines` 长度
区分，也不把一个上下文的所有候选塞进同一条记录。

## 微章节

拍一拍既可以得到一句完整回应，也可以进入一个两至三句为主的微章节。微章节不是对话树，用户不
选择答案；每次冷却外的有效点击只承担“继续听 Pibo 把这件事说完”。适合使用微章节的内容通常
具有清楚的递进，例如：当前事实 → Pibo 联想到自己 → 一个具体疑问、误会或反转。没有递进的普通
回应和称赞继续使用单句，不能为展示机制强行拆成多拍。

当前版本没有文字输入、选项回答或语音回答。Pibo 可以说“你是想看我动一下？”之类由当前点击
本身已经回答的反应性问句，也可以提出随后由自己继续思考的疑问；不能提出“路上看到了什么？”
并等待用户提供内容，更不能在没有输入能力时假装听见、记住或回应用户的答案。真正需要用户回答的
关系对话作为后续能力单独设计，不用拍一拍继续机制冒充双向对话。

- 第一拍选中互动单元、显示第一句并执行该记录的 `action`；
- 后续拍只推进下一句，不反复重启 `action`；
- 非最后一句由内容层提供 `hasNext`，平台可用轻量省略号提示仍有下句，不依赖新图片素材；
- 不自动续播；用户停止点击时，Pibo 也停在当前句；在首页保持且主状态未变化时，下一次有效点击
  继续当前微章节，不增加短超时；
- Core 主状态改变或离开首页会终止当前微章节。未完成的事件互动不标记为已回应；以后再次满足资格
  时从第一句重新开始，不能脱离开头直接恢复结尾；
- 同一主状态下出现的新事件等待当前微章节完成后再回应；真正的主状态变化仍立即打断；
- 最后一拍完成后才移动该情境的记录游标，并在事件情境中把事件标记为已回应。

## 台词的结构约束

每条台词必须有一个用户能立即理解的触发点和交谈目的。用户不应依赖隐藏设定、状态名或作者解释，
才能明白 Pibo 为什么此刻说这句话。可以是对这次点击的直接回应，也可以来自当前行为或一个实时
健康事实；不再要求每句话同时承担“锚点、转义、纹理”，更不能为了显得有角色感而补抽象判断。

一句只使用一个主要实时事实或数字，不把气泡写成健康报表。机制可以在确实被触发时直接说出来，
但不能仅凭机制强行制造笑话。幽默必须来自当前真实情境、Pibo 的具体误会或双方正在发生的互动；
没有情境时就正常说话。系统权限、硬件、同步和识别失败继续由系统 UI 准确说明，不强迫 Pibo 充当
错误提示器。

## 气泡、冷却与生命周期

- 一次有效点击必须得到一条符合当前状态的回应；正常说话没有每 10 分钟或每日上限。
- 气泡显示时长就是点击冷却时长；冷却中的点击直接忽略，不排队、不计数、不振动、不延长冷却。
- 当前版本只制作中文；气泡时长与冷却只按中文体验确定。Reduce Motion 可以改变呈现动画，
  但不改变冷却。
- Core 主状态改变时立即清除当前气泡和冷却，下一次点击使用新状态。
- 离开首页时清除气泡和冷却；仅在同一首页上打开其他功能或 Sheet 时，气泡和冷却照常结束。
- Core 主状态改变或离开首页也会清除未完成微章节；同页 Sheet 不重置微章节进度。
- 无专用姿态或动画不阻塞本机制。`action` 保留稳定语义，新动作资源作为 TODO 单独设计。

## 替代与否定

本决定替代旧 Pat V2 在日常拍一拍上的以下规则：概率说话、第三次点击必然生气、普通台词
每 10 分钟／每日上限、用随机值或手工 ID 去重。快速重复点击首期由气泡等长冷却处理，不新增
`angry`、`disturbed` 或 `overstimulated` 主状态，也不把它们作为当前文案必备子状态。

本决定也不采用“普通／傲娇／搞笑”多套人格皮肤。Pibo 必须保持一个稳定身份；六个主状态
后续只改变它的当下判断、注意力和行动，不把 Pibo 写成六种人格。

## `stable` 首版冻结

`stable` 首版只建立两个真实行为子状态：

- `idle`：进入 `stable` 后的默认行为；
- `thinking`：Pibo 在首页连续 30 秒没有收到用户互动后进入的轻量行为。

`checkIn` 是一次点击触发的瞬时动作，不是持久子状态。步数、睡眠等新事实属于事件情境；首次接触
序列属于关系发现情境，也不伪装成行为子状态。首版不增加 `bored`、`comforted`、`disturbed`、
`angry` 或没有可见行为支撑的“观察物件”等子状态。

`thinking` 首版不需要新姿态或主动气泡。有效点击读取点击前的行为子状态，选择一条
`stable.thinking` 回应，然后返回 `idle`。它可以在下一次连续 30 秒无互动后再次进入；Core 主状态
改变、离开首页或进入其他功能时清除本次 `thinking`。同页 Sheet 对已出现气泡／冷却的处理仍遵守
上节规则，不因清除行为子状态而提前撤掉气泡。

`stable` 的选句优先级冻结为：

1. 尚未回应的新健康事件；
2. 尚未完成的首次接触发现序列；
3. 点击前的当前行为子状态；
4. `stable.idle` 普通循环。

事件回应与有效点击都会结束本轮 `thinking`。首次接触发现使用固定顺序推进，但它不是次数上限；
发现完成后继续进入普通池，每次冷却外的有效点击仍然有回应。

首批中文内容冻结如下。当前每条都是单句互动单元；情境内的多个单元按固定记录游标循环，不把
相邻编号解释为一个微章节：

### `stable.touchDiscovery`

1. `这边也能碰到？`
2. `好吧，我也碰不到你。`
3. `这算打招呼吗？`

### `stable.idle`

1. `怎么了？`
2. `你是在叫我吗？`
3. `你刚才是故意的吗？`
4. `我还以为你要点旁边。`

### `stable.thinking`

1. `我刚才没有发呆。`
2. `我正在想事情。现在忘了。`
3. `我没睡。只是没动。`

### `stable.stepsEvent`

1. `我看到今天有 {steps} 步了。`

### `stable.sleepEvent`

1. `昨晚睡了 {sleepDuration}。`
2. `你睡了 {sleepDuration}，我当时也睡着了。`

第二条睡眠文案只有在 Core 能确认 Pibo 在对应时间也处于 `sleeping` 时才有资格出现。动态事实本身
已经提供变化，首版不为同一数字强行制作多套聪明说法。上述数量是可实现的首版下限，不是长期
容量上限；后续可以在同一声音标准下继续补充，不因此重新打开已冻结的状态和调度结构。

## `energetic` 首版冻结

瞬时 `playing`；新运动、活动里程碑或良好睡眠事件优先回应一次，第一拍执行 `play`，微章节后续
拍只推进文字，结束后回到 `ready`，不改变持续的 `energetic` Core 主状态。

可用性问题需重新打开该决定，不能由平台单独漂移时长。

## `tired` 首版冻结

`tired` 首版只由 Core 的 `insufficientSleep` 原因触发，低步数、未运动和数据缺失不能进入疲惫。
行为结构为默认 `awake`，首次有效休息互动后进入 `resting`；`resting` 只表示 Pibo 被安顿下来，
不会把 Core 主状态改成 `stable`，也不设置倒计时伪造恢复。

### `tired.insufficientSleep`

1. `昨晚睡得有点少。`
2. `难怪我今天总想坐下。`

### `tired.awake`

以下三个互动单元按记录游标循环：

- `我今天有点困。`
- `我没有睡着。` → `只是眼睛不太想睁开。`
- `我本来想站直一点。` → `还是下次吧。`

### `tired.resting`

1. `这样舒服一点。`
2. `我就坐一会儿。`

“我还醒着。”→“只是暂时不想起来。”方向本身可用，但未选入首版，可作为后续扩容候选。
有无吊床当前共用内容；鸿蒙已有的短暂下沉承担首版进入 `resting` 反馈，地面／吊床正式动作资源
继续留 TODO。

`resting` 在同一次 `tired` 主状态期间跨首页和 App 重启保持，避免每次打开都要求用户重新安顿。
离开首页仍清除气泡、冷却和未完成微章节，但不清除 `resting`。再次拍击只播放
`tired.resting` 内容，记录使用 `action: none`，不重复执行下沉或暗示再次治疗。Core 主状态改变时
清除；下一次经过 `sleeping → waking → tired` 形成新的疲惫周期时，重新从 `awake` 开始。

## `waking` 首版冻结

`waking` 是 Core 控制的固定初醒过渡期，互动不能提前结束它，也不能提前宣布待落地的
`stable / energetic / tired / dataUnknown`。首版行为结构为尚未完成早安互动的 `orienting` 与
已经完成的 `greeted`；Core 待落地结果为 `tired` 时，`orienting` 使用 `recovering` 内容分支，
但不增加第三个持久子状态。

当前初醒周期第一次有效拍击执行 `morningGreeting`，完整说完首个互动单元后进入 `greeted`。
`greeted` 跨首页和 App 重启保持，但只绑定当前 `wakeStartedAt`；后续互动使用 `action: none`，
不反复伸展。新主状态覆盖时清除；初醒结束时未说完的微章节立即中断，不补播。有无吊床使用现有
不同画面，但共用文案。

### `waking.orienting`

以下两个互动单元按初醒周期记录游标轮换：

- `早上好。`
- `早上好。` → `我刚醒。` → `先让我站稳。`

### `waking.recovering`

1. `早上好。`
2. `醒是醒了。`

以下两个互动单元按记录游标循环：

- `早上好已经说过了。` → `再说一次也可以。`

## `sleeping` 首版冻结

`sleeping` 本身已经是完整行为，首版不增加 `disturbed / angry / halfAwake` 等子状态。普通拍击不能
真正叫醒 Pibo；是否进入 `waking` 只由 Core 决定。每次有效拍击执行轻量 `letSleep` 并显示一个
单句互动单元，不使用微章节或继续提示，避免为了听完内容鼓励连续拍击。

有吊床与无吊床共用内容，不比较舒适程度。状态变为 `waking` 时立即清除气泡和冷却；不使用抱怨、
责备或把快速点击转成受苦的文案。

### `sleeping.asleep`

以下六个单句互动单元按记录游标循环：

- `呼……`
- `还没醒。`
- `我睡得正香呢。`
- `等我醒了再说。`
- `晚安。`
- `我正在睡。很认真。`

## `dataUnknown` 首版冻结

`dataUnknown` 是无法可靠判断当前状态时的安全回退，不是疲惫、受苦或低健康表现，也不复用
`tired` 的姿态与内容。首版不增加行为子状态，也不使用微章节；权限、等待数据、服务不可用和
无可信历史时的同步中断是诊断原因，不是 Pibo 的性格或行为变化。

每次有效拍击都执行 `checkConnection`。先让 Pibo 的短句完整可读，再打开现有健康状态 Half Sheet，
避免系统面板抢掉角色回应；用户关闭面板后再次有效拍击仍可重新检查和打开面板，不设置只执行一次的
`checked` 状态。Pibo 只表达自己暂时不知道或不能判断，准确原因、权限入口、设置、重试和自动恢复
说明继续由系统 UI 提供。

### `dataUnknown.authorization`

- `我还看不到睡眠和活动记录。`

### `dataUnknown.waitingData`

- `记录还不够。我先不乱猜。`

### `dataUnknown.unavailable`

- `新的记录暂时拿不到。`

### `dataUnknown.interruptedNoTrustedState`

- `新的记录断了。我还不能判断。`

如果同步暂时中断但仍有可信历史状态，Core／平台继续保留上次可信的真实主状态，并使用现有可点击
Banner 解释中断；此时不进入 `dataUnknown`，也不播放上述内容。没有数据不能被解释成低健康、不能
扣除或阻止 `bo`，也不能责备用户。原因恢复并产生可靠主状态时立即清除当前气泡、冷却和检查动作。
