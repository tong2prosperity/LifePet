# Pibo 当前实现现状、产品目标与问题审计 v0.1

> 日期：2026-08-17  
> 状态：现状审计与后续排查入口，不是新的最终 PRD  
> 范围：iOS 当前工作树、已发布的 `pibo-core 0.13.2` 规则、当前叙事决定与近期用户重新定义  
> 目的：让后续产品、设计、动画和工程工作首先理解“现在已经有什么、真正要做什么、为什么仍然不像一款完整养成产品”

## 0. 阅读结论

当前 Pibo 不是从零开始。工程已经具备健康数据采集、跨平台状态规则、`bo` 计分与账本、
拔取、永久物件、功能解锁、拍一拍、餐食拍照与卡路里识别、Walk Doodle、历史、通知、
Widget 和固定森林首页。

当前最主要的问题也不是“缺少更多功能”，而是以下三条链尚未闭合：

1. **状态到照料**：用户看见 Pibo 的状态后，不知道除了拍一拍还能做什么；
2. **`bo` 到 Pibo 成长**：`bo` 能兑换永久物件和能力，但成长主要落在库存、物件和入口，
   没有稳定地落回 Pibo 的身体与自主行为；
3. **功能到共同生活**：餐食相机等功能技术上已经成立，但使用完成后 Pibo 没有参与，
   因而像附加工具，不像养宠物的一部分。

2026-08-17 的最新产品定义是：

> **用用户真实的健康数据养一只 Pibo，并大量借鉴拓麻歌子的养成逻辑。**

这条定义与早期正式决定中“Pibo 不是宠物、不是被照顾者”的表述存在直接冲突。最新用户
决定在当前工作中优先，但仓库尚未形成替代决定，因此现阶段必须把它视为一个需要正式收口
的产品身份迁移，而不能继续同时使用两套互相矛盾的解释。

最小可行方向不是增加饥饿、清洁、心情、亲密度等数值条，而是复用现有系统形成：

```text
真实睡眠与活动
→ Pibo 出现可读的当前状态
→ 用户执行一个与状态相符的轻量照料动作
→ bo 生长、成熟并被拔取
→ bo 解锁共同物件
→ Pibo 永久学会使用该物件
→ 相机、散步等能力成为双方共同生活的一部分
```

## 1. 文档边界与事实分级

本文使用四种状态描述，避免把愿景写成已经交付：

| 标记 | 含义 |
|---|---|
| 已实现 | 当前代码和资源中存在完整或可运行链路 |
| 已冻结 | 产品规则已经确认，并由权威文档或 Core 固定 |
| 部分实现 | 底层或入口存在，但用户体验、资源或闭环不完整 |
| 未决 | 仍需产品决定，当前不得由平台端或美术自行补全 |

另外，本文记录的是 **2026-08-17 当前工作树**。工作树包含尚未提交的 `pibo-core 0.13.2`
迁移、状态生命周期、无吊床睡眠／初醒资源和测试改动。它们已经出现在本地实现与 HANDOFF，
但不能自动等同于已合并、已发布 App Store 或已完成真机验收。

## 2. 当前产品目标

### 2.1 对外最容易理解的承诺

> 不用反复点击喂食。你的真实睡眠和活动，会养出一只属于你的 Pibo。

“健康数据养宠物”负责让用户在第一次接触时理解产品；健康报表、主线故事、物件词典和
卡路里工具都不能取代这条第一承诺。

### 2.2 目标体验

用户每次打开 App，应该能回答三个问题：

1. Pibo 现在怎么样；
2. 我现在可以为它做什么；
3. 它因为我们过去的生活，永久变成了什么。

对应三种时间尺度：

- **即时**：睡眠或运动使 Pibo 的身体和动作发生明显变化；
- **数日**：头顶 `bo` 发芽、成形、成熟并可拔取；
- **长期**：Pibo 获得永久行为、共同物件和只属于该用户的生活历史。

### 2.3 当前不应承诺的内容

当前还不能承诺：

- Pibo 会记住用户的一切；
- Pibo 已经具有完整成长形态或个性分化；
- 低健康一定会使 Pibo 进入更严重的受苦阶段；
- 餐食卡路里会影响 Pibo 的身体、`bo` 或健康判断；
- Shadow Pibo、好友、战斗、商店或长期付费养成已经存在。

## 3. 当前产品信息架构与发布开关

### 3.1 首页

当前 Home 是一个固定竖屏 SpriteKit 森林：

- 没有 Studio；
- 没有 Gym；
- 没有横向漫游、吸附或惯性；
- SwiftUI 负责顶部／底部 Chrome、Modal、Sheet 和 Full Screen Cover；
- SpriteKit 负责森林、Pibo、物件、反射、光照和角色动画。

首页当前主要可见行为是：

- 查看 `bo` 余额和生长进度；
- `bo` 成熟后拔取；
- 打开共同物件页面；
- 拍一拍 Pibo；
- 打开历史；
- 能力已解锁时显示相机和 Walk Doodle 入口；
- 点击已拥有的森林物件进入对应能力。

### 3.2 Release 开关现状

来源：`Pibo/App/PiboReleaseScope.swift`。

| 功能 | Release 基础值 | 额外门槛 | 当前结论 |
|---|---:|---|---|
| 新六场面临时合作 Onboarding／事件 01–03 | 关闭 | 无 | 代码和持久化保留，当前发布使用旧 Onboarding |
| 餐食相机 | 开启 | 必须拥有补梦风铃／`.dewCamera` | 技术链可用，但新用户不能立即看到入口 |
| Walk Doodle | 开启 | 必须拥有补梦风铃／`.walkDoodle` | 独立工具，不属于小游戏 |
| 其他小游戏 | 关闭 | 无正式入口 | `Games/` 是工程库存，不是当前 Gym |
| 新足迹历史 Tab | 关闭 | 无 | 当前 History 仍以既有版本为主 |
| 自定义 Pibo | 关闭 | 无 | 代码库存不属于当前养成核心 |

需要特别注意：`camera == true` 不等于用户一定能看到相机。最终可用条件是：

```text
PiboReleaseScope.camera
&& OrnamentUnlockStore.grants(.dewCamera)
```

## 4. 当前实现全景

### 4.1 跨平台规则与职责

`pibo-core` 是以下确定性规则的唯一来源：

- 状态生命周期与健康阈值；
- 睡眠结果、动态作息和运动发现窗口；
- `bo` 每日计分、成形阈值和结转；
- 拍一拍、拔取、内容键和动画语义；
- 共同物件的价格、顺序、前置和 capability；
- 其他已进入 SDK 的跨平台纯逻辑。

iOS 负责：

- HealthKit 数据获取与来源过滤；
- Core 输入映射和快照持久化；
- SwiftUI／SpriteKit 表现；
- 图片、动画、音效、触感和通知；
- SwiftData 历史；
- 相机、位置、网络和 StoreKit。

当前工作树固定 `pibo-core 0.13.2`。任何新的跨平台状态、成长阶段阈值、语义动画选择或
能力目录变更，必须先在 Core 完成并发版，再更新 iOS exact pin 和 HarmonyOS submodule。

### 4.2 健康数据与主状态

当前 Core 语义主状态为：

| 状态 | 含义 | 当前视觉 |
|---|---|---|
| `dataUnknown` | 没有足够可靠数据 | 暂时复用稳定姿态 |
| `sleeping` | 处于 Pibo 的动态睡眠周期 | 有吊床使用吊床睡眠；无吊床使用地面睡眠 |
| `waking` | 醒来后的 60 分钟过渡 | 吊床初醒已接；无吊床恢复不足已接；普通无吊床暂回退稳定姿态 |
| `stable` | 有数据但没有新的强状态事件 | 正式稳定待机 |
| `energetic` | 良好睡眠、运动或 8,000 步里程碑造成正向变化 | **语义存在，但当前统一回退稳定姿态** |
| `tired` | 睡眠恢复不足 | 正式疲惫待机已接 |

当前生命周期不是实时重算一张复杂优先级表，而是按事实发生时间处理事件：

- 最近一次有效状态变化覆盖此前状态；
- 运动发现窗口结束或步数跨日重置不会自动让精力充足消失；
- 同状态新事件更新原因并可播放事件反应，不必闪切状态；
- 初醒没有被新事件打断时，60 分钟后落地本次睡眠结果；
- 迟到的历史回填不能用“同步时间”覆盖更晚的真实事件；
- App 重启后恢复 Core 快照，而不是从当前瞬时条件重新发明状态。

已冻结的关键数值：

- 单晚低于 `max(个人睡眠基线 × 65%, 4.5 小时)` 触发疲惫；
- 连续两晚低于基线 80% 也触发疲惫；
- 一晚达到基线 95% 可从疲惫恢复；
- 良好睡眠要求高于基线 30 分钟且至少 6.5 小时；
- 无个人基线时使用 7 小时；
- 活动里程碑为当日首次跨过 8,000 步；
- 近期运动首次发现窗口为结束后 3 小时；
- 动态个人作息要求至少四晚且规律性达到 60。

规则本身已较完整，当前主要缺口是 **`energetic` 没有可辨认的正式视觉资源**。这直接导致
“正向变化必须落在 Pibo 身上”的核心承诺目前无法完整验证。

### 4.3 Pibo 渲染与动画

当前默认角色渲染是矢量路径运行时，不是直接显示 SVG 文件：

```text
pibo-media 状态 SVG
→ 构建时统一采样和拓扑匹配
→ PiboCharacterData.json
→ SpriteKit SKShapeNode
→ 路径插值、Crossfade、Spring 与 Warp 动画
```

身体、`bo` 和主要轮廓可进行路径变形；部分五官和装饰使用淡变。PNG／纹理路径仍保留作
兼容和特效用途，但当前主角色不是一组 PNG 序列帧。

当前工作树的关键资源状态：

- 稳定：已接；
- 疲惫：已接；
- 吊床睡眠／初醒：已接；
- 无吊床睡眠：4.8 秒基础呼吸循环已接；
- 无吊床恢复不足初醒：7.2 秒循环已接；
- 普通无吊床初醒：暂时回退稳定姿态；
- 精力充足：未审定资源已经撤出运行时，语义暂回退稳定；
- 数据未知：MVP 复用稳定姿态。

### 4.4 `bo` 形成、成熟与拔取

当前 `bo` 已经是完整的本地优先经济账本：

- 只使用通过来源校验的真实健康记录；
- 未登录和离线不阻止形成；
- 从许可／旧 Onboarding 边界后的下一个完整自然日开始计入；
- Core 按日计分，App 不复制阈值；
- 连续能量池达到 Core 阈值后铸成可拔取 `bo`；
- 可同时存在多枚成熟待拔取；
- 成熟 `bo` 永不过期；
- 拔取幂等地从 `ripeCount` 进入余额；
- 余额可消费，已有成长不因重新启用故事许可而丢失。

App 已经暴露：

- `growthProgress`：当前一枚 `bo` 的 0...1 生长进度；
- `hasRipeBo`：是否存在成熟可拔取 `bo`；
- `balance`：已经拔取、可以消费的数量；
- `lifetimeMinted`／`lifetimeCollected`：生命周期统计。

但用户体验上仍存在三个问题：

1. 连续进度尚未被稳定解释成“发芽—成形—成熟”的清楚生命阶段；
2. 被拔取的 `bo` 是同质、可互换的余额，不保存这枚 `bo` 的独特生长历史；
3. 拔取后的主要结果是消费和解锁物件，Pibo 本身没有统一的永久成长表达。

### 4.5 共同物件与永久能力

当前物件由 Core 固定顺序、价格和前置：

| 顺序 | 物件 | 价格 | 永久 capability |
|---:|---|---:|---|
| 1 | 吊床 | 1 `bo` | 睡眠回顾、睡醒通知 |
| 2 | 补梦风铃 | 5 `bo` | 露珠相机、Walk Doodle |
| 3 | 状态观测仪 | 5 `bo` | 恢复状态 Modal |
| 4 | 铃兰灯 | 15 `bo` | 魔法点灯、未来 Shadow Pibo 资格 |

购买必须按顺序；因此补梦风铃／相机的累计前置成本是 6 `bo`。

物件系统已经具备：

- 永久所有权；
- 原子扣款和崩溃恢复；
- 解锁预览、放置、回到森林后的发现；
- capability 的显示层与路由层双重校验；
- 缺数据／拒绝通知时的降级说明；
- 森林中的实际落位与交互。

它已经是“永久成长”的工程骨架，但目前更像功能解锁目录。为了服务宠物养成，最少需要让
Pibo 持续表现出自己学会使用这些物件：疲惫时主动去吊床、风铃解锁后观察餐食投影、主动
靠近观测仪、回应铃兰灯。这样无需新建能力树，也能让永久变化落回 Pibo。

### 4.6 当前用户互动

已经存在：

- 拍一拍与连续打扰反应；
- 普通台词、保护态台词预算和内容键；
- `bo` 成熟后的拔取；
- 点击共同物件；
- 点击灯、相机、Walk Doodle、历史和设置；
- 新运动、活动里程碑、`bo` 变化的事件反馈。

缺少：

- 根据当前状态给出的单一上下文照料动作；
- 用户照料后 Pibo 在空间里完成一个自主行为；
- 不改变健康事实、但能让用户感到“我刚刚照料了它”的结果；
- 多次打开后有记忆的状态内行为轮换。

这意味着当前用户更像在查看和触发功能，而不是在照料一只正在生活的 Pibo。

### 4.7 餐食相机与卡路里记录

当前相机链路已经实现：

```text
选择餐次
→ 真实相机拍摄
→ Vision 抠出食物主体并保存透明 PNG
→ 原始完整画面上传后端 VLM
→ 返回菜名、总热量、食物明细、蛋白质、碳水、脂肪与备注
→ 结果写回 FoodPhoto
→ MealDetailView 和历史展示
```

现有安全／失败边界：

- 权限拒绝、设备不可用、拍摄失败时不伪造照片；
- 相机只在取景阶段占用硬件；
- 快速退出、重拍和旧回调有生命周期隔离；
- 识别失败保留照片并允许重拍；
- VLM 识别是分钟级异步任务，Modal 可先展示加载；
- 拍照、游戏和付费当前都不生成 `bo`。

当前产品断点：拍完后主要进入餐食详情，Pibo 没有观察、回应或记住这次共同经历。因此相机
目前是一项实用工具，而不是宠物养成行为。

最少改动的结合方式是“共餐／地球食物观察”：

1. 点击补梦风铃或现有相机入口；
2. 拍摄并保存现有 `FoodPhoto`；
3. 返回森林后，复用透明食物抠图短暂出现在 Pibo 身边；
4. Pibo 播放一次靠近、低头观察或记录的短行为；
5. 识别完成后出现简短结果，点击仍进入现有 MealDetail；
6. 照片和卡路里继续永久进入历史。

餐食记录可以影响 Pibo 的观察行为和共同生活记录，但首期不应影响 Pibo 生死、主状态、
`bo` 产量或对用户饮食的道德评价。识别值是估算，用户也不会完整拍下每餐；把它变成惩罚
或养分会制造错误激励和记录压力。

### 4.8 Walk Doodle

Walk Doodle 已作为独立步行创作工具存在，并与小游戏发布开关分离。它需要补梦风铃
capability，主动记录时才请求精确位置；只获得大概位置时不开始记录。结果可以写入历史。

它目前与 Pibo 的长期行为关系同样较弱。后续最小结合是让 Pibo 在开始／完成路线时出现
一次共同出发或查看线条的反应，而不是另建 Gym 或小游戏经济。

### 4.9 历史、Widget、Live Activity、Watch

- History 已能保存健康记录、餐食照片、餐食识别结果和 Walk Doodle 记录；
- 新“足迹”Tab 的 Release 开关当前关闭；
- Home Widget 和运动 Live Activity 消费新的状态语义和同步时间；
- Watch App 当前只保留独立 CRC 呼吸训练，不向手机流式传输状态；
- 旧 WatchConnectivity、旧 Vital wire format 和旧音乐／会话方向不得继续扩展。

### 4.10 Onboarding、故事与关系

新六场面 Onboarding、故事 checkpoint、中断恢复和事件 01–03 已经实现，但 Release 当前
关闭，产品暂时回到旧 Onboarding。关闭期间的健康事实、`bo` 和故事观察边界已经分开持久化，
未来重新打开不会错误补推故事。

二十一个主线事件已经有完整大纲，但当前优先级不是继续制作事件 04，而是验证最小养成循环。

更重要的是，早期叙事决定把 Pibo 定义为共同经历者和镜子，不是宠物、幼儿或被照顾者；
最新用户决定则明确采用“用健康数据养一只 Pibo”和拓麻歌子逻辑。后续必须正式替代或修订
关系模型，否则 Onboarding、台词、受苦、照料动作和商业化会持续使用互相矛盾的标准。

## 5. 目标与当前实现的差距

| 产品目标 | 当前实现 | 主要差距 | 影响 |
|---|---|---|---|
| 用户五秒看懂健康改变了 Pibo | 睡眠、疲惫等已有；精力充足回退稳定 | 最关键的正向状态不可见 | 核心承诺无法完整验证 |
| 用户知道现在能为 Pibo 做什么 | 拍一拍、拔 `bo`、点功能入口 | 没有状态对应照料动作 | 打开后缺少主动性 |
| `bo` 像一个会成长的生命结果 | 有连续进度、成熟和拔取 | 阶段语义弱，拔取后立即货币化 | 容易像积分条 |
| 成长永久落在 Pibo 身上 | 物件和能力永久存在 | Pibo 不稳定地使用物件或获得行为 | 养成感弱于功能解锁感 |
| Pibo 不打开 App 也在生活 | 有睡眠、初醒、昼夜和部分事件 | 自主行为数量少，重复打开差异有限 | 容易像动态 Widget |
| 餐食相机属于双方共同生活 | 拍摄、识别、详情、历史已完成 | Pibo 没有参与拍摄后的结果 | 相机像独立工具 |
| 养成简单直接 | 系统层很多且历史文档复杂 | 镜子、返航、物件、故事、健康工具并列 | 用户难以形成单一心智模型 |
| Pibo 可以受苦但不逼迫用户 | 疲惫存在，死亡／伤害未实现 | 触发程度、恢复、缺数据和反强迫边界未整体替代 | 动画和通知无法安全扩展 |
| 相机能成为较早留存点 | Release 开启但补梦风铃需累计 6 `bo` | 可能太晚才被发现 | 首周价值不可见 |

## 6. 当前最重要的问题与困境

### 6.1 产品身份冲突：镜子还是宠物

“共同经历者／镜子”强调对等、克制和不要求用户照料；“拓麻歌子式宠物”强调需求、照料、
后果和成长。两者可以融合，但不能继续假设天然一致。

需要明确的新关系是：

> Pibo 是有自主性和自尊的宠物型伙伴。它的身体由用户真实生活影响，用户可以照料它，
> 但它不是幼儿、任务发布器或用痛苦勒索用户的健康教练。

这句话目前只是建议解释，尚未形成替代决定。

### 6.2 被动数据和主动养成之间缺一层

健康数据在 App 外自动发生，这是 Pibo 的差异化优势，也是养成参与感不足的原因。不能靠
增加签到和虚拟喂食解决，否则真实健康数据会失去意义。

需要增加的是“照料表现”，不是“照料数值”：用户让疲惫的 Pibo 去休息、在初醒时轻触、
回应精力充足的探索、拔取成熟 `bo`。点击改变行为和关系，不伪造健康事实。

### 6.3 规则已完整，但最关键美术仍缺

Core 已能输出 `energetic`，但当前 App 将它显示成稳定。技术上状态正确，用户视觉上却看不出
正向变化。这类问题容易在排查时被误认为 Core 错误，实际上是“语义状态和资源呈现不等价”。

### 6.4 `bo` 是成熟经济系统，但不是完整养成结果

Core 评分、账本、幂等、离线、跨日和消费已经很成熟；用户价值却仍未闭合。继续优化计分
精度，不能替代“第一枚 `bo` 到底让 Pibo 永久学会什么”的产品决定。

当前最省改动的答案是把第一枚 `bo` → 吊床解释成第一项永久成长，并让 Pibo 以后真实使用
吊床。后续物件同理。

### 6.5 硬解锁与功能发现存在矛盾

共同物件让成长具有目标，但未拥有入口完全消失，使高价值工具可能长期不可见。相机目前
累计需要 6 `bo` 才能获得。如果相机是路线图附加能力，这没有问题；如果相机是首周留存和
潜在长期付费能力，这个时机可能过晚。

必须在以下两条中选择：

- 相机是后期奖励：保留当前成本和隐藏逻辑；
- 相机是核心留存能力：保证在第二或第三枚 `bo` 附近出现，或调整为基础相机＋风铃增强。

### 6.6 Pibo 可以受苦，但边界尚未替代完成

当前只确认 Pibo 可以出现负面条件，尚未冻结完整严重度和恢复体系。当前仍不能自行增加：

- 死亡；
- 不可逆伤害或能力丢失；
- 未打开 App 导致衰败；
- 缺权限导致痛苦；
- “你走得太少，所以 Pibo 被你伤害”的直接归责；
- 指责、倒计时和连续负罪通知。

在新决定形成前，疲惫可作为身体事实和可恢复内容，但不能扩成惩罚经济。

### 6.7 故事规模大于已验证的日常循环

一年主线、返航、故乡历史和关系弧已经相当完整，但用户是否愿意回来查看 Pibo、拔第一枚
`bo`、使用第一个永久物件仍未通过真实用户验证。继续推进事件 04 会增加内容量，却不会回答
日常打开理由是否成立。

### 6.8 历史工程存量增加理解成本

仓库仍保留部分旧三状态／星光／建议卡、旧小游戏、旧自定义和兼容字段。当前 Home 已不再
显示旧三状态，但类型仍可能被其他代码和测试引用。

必须遵循：

- 不重新启用 `StatKind`、活力星光、静息星光、心绪回声和今日步骤卡；
- 不把 `Games/` 当作等待恢复的 Gym；
- 不从旧文档重建 Studio、横向漫游或数据二楼；
- 兼容字段可以保留，但不能作为新产品概念来源。

## 7. 较少改动的建议实现

### 7.1 不新增完整宠物数值系统

当前不建议新增：

- 饥饿值；
- 清洁值；
- 心情条；
- 亲密度条；
- 食物库存；
- 菜谱／厨房；
- 第二种货币；
- 每日三餐强制任务；
- 新的 Pibo 健康状态机。

这些系统会复制现有健康和 `bo` 逻辑，并显著增加用户负担。

### 7.2 用现有状态增加一个上下文动作

| 当前状态 | 首页动作 | 允许改变 | 不允许改变 |
|---|---|---|---|
| 疲惫 | 让它靠一会儿 | 位置、动作、短期舒适表现 | Core 健康状态 |
| 初醒 | 等它清醒／轻轻碰它 | 初醒回应 | 睡眠结果 |
| 稳定 | 拍一拍／观察 | 台词与状态内行为 | 健康事实 |
| 精力充足 | 回应它／陪它活动 | 探索行为 | 伪造运动数据 |
| `bo` 成熟 | 拔取 | 账本和成长事件 | 当前健康状态 |

首期每个状态一个动作即可，不做动作菜单。

### 7.3 用现有 `bo` 进度显示三个阶段

把现有 `growthProgress` 映射为 Core-owned 语义阶段：

```text
sprouting → forming → ripe
```

iOS 与 HarmonyOS 只选择对应视觉，不分别定义业务阈值。现有头顶路径、伸展和拔取动画可以
继续使用，不需要创建独立宠物胚胎系统。

### 7.4 把物件所有权解释为 Pibo 的行为能力

- 无吊床：疲惫时在地面休息；有吊床：主动去吊床；
- 无风铃：没有图像观察；有风铃：拍照后观察食物投影；
- 有观测仪：会主动靠近、检查或校准；
- 有铃兰灯：会观察或回应用户点亮的灯。

永久变化由物件所有权直接派生，不新增另一套 `PiboAbilityInventory`。

### 7.5 把餐食相机接回森林

复用现有 `FoodPhoto.pngData` 和识别结果，增加一个幂等的 `mealRecorded` 呈现事件：

```text
拍摄完成
→ 返回森林
→ 食物抠图短暂出现
→ Pibo 观察
→ 识别完成后展示简短结果
→ 点击进入现有 MealDetail
```

首期只需一段观察行为和一个结果气泡，不需要重做服务器、相机、历史或餐食详情。

### 7.6 调整首次永久反馈和相机时机

- 第一枚 `bo` 继续解锁 1 `bo` 吊床；
- 解锁后必须立即在首页展示 Pibo 能使用吊床；
- 如果相机属于首周留存，补梦风铃应不晚于第二或第三次成熟；
- 价格／顺序正式调整必须先修改 Core 目录并按双端发布流程迁移。

## 8. 排查问题时的最短路径

### 8.1 Pibo 状态不对

按顺序检查：

1. `HealthDataService` 是否收到了真实、时间正确、来源可信的事实；
2. `PiboCoreStateAdapter` 是否以事实发生时间构造事件；
3. `PiboStateLifecyclePersistence` 是否恢复了正确快照；
4. Core decision 的语义状态和 cause 是否正确；
5. `HomeAnimationInputResolver` 是否把 decision 交给表现层；
6. 不要先从 SpriteKit 资源名称反推健康状态。

### 8.2 Core 状态正确，但画面不对

检查：

1. `PiboCoreAnimationAdapter` 的语义状态到资源映射；
2. `PiboAnimationStateMap.available` 是否包含目标资源；
3. 是否因为没有吊床而切到地面分支；
4. 是否处于 `waking` 且带 `pendingState == tired`；
5. 是否命中明确回退：`energetic → stable`、普通地面 waking → stable；
6. `PiboCharacterData.json` 和 `PiboMedia.lock` 是否同步。

### 8.3 `bo` 不增长、重复增长或不能拔取

检查：

1. 当前 release 是否启用 `eligibilityEnabled`；
2. `acceptedAt`／旧 Onboarding 边界和 `firstEligibleAt`；
3. 是否为边界后的完整自然日；
4. 健康记录是否为 verified、非 Demo／合成来源；
5. `PiboCoreBoAdapter` 输入是否能表达该日数据；
6. `grantedEnergyByDay` 是否已经记录该日；
7. Core `scoreDay` 与 `applyEnergy` 的结果；
8. `ripeCount`、`processedCollectionEventIDs` 和 `balance`。

### 8.4 相机或 Walk Doodle 入口不出现

同时检查两层：

1. `PiboReleaseScope.camera`／`.walkDoodle`；
2. 是否已经拥有补梦风铃；
3. `OrnamentUnlockStore.grants(.dewCamera/.walkDoodle)`；
4. `HomeFeatureAccess` 的最终 `cameraEnabled`／`walkDoodleEnabled`；
5. Presentation binding 和路由是否再次执行门控。

### 8.5 新 Onboarding／事件 01–03 不出现

先检查 `PiboReleaseScope.temporaryCooperationOnboarding`。当前 Release 默认关闭，这是预期行为，
不是故事状态损坏。

### 8.6 餐食照片有了，但没有卡路里结果

检查：

1. 拍摄是否带 `MealType`，自由拍摄不会启动餐食识别；
2. 是否成功保存透明抠图 `FoodPhoto`；
3. `FoodRecognitionService.analyzing` 是否仍在进行；
4. 原图 JPEG 是否编码成功；
5. `/api/v1/food/recognize` 是否成功返回；
6. `analysisJSON`、`dishName`、`totalCalories` 是否写回；
7. 识别失败时应保留照片并显示重拍，而不是生成虚假结果。

## 9. 当前必须拍板的问题

按阻塞程度排序：

1. **关系模型替代**：如何正式把“不是宠物”修订为“有自主性和自尊的宠物型伙伴”；
2. **第一照料动作**：疲惫、初醒、稳定、精力充足分别只保留哪个上下文动作；
3. **精力充足美术**：正式关键姿态、基础循环和进入反应；
4. **第一枚 `bo` 的永久结果**：是否正式确认“吊床＋Pibo 主动使用吊床”就是首个成长闭环；
5. **`bo` 三阶段**：阶段名称、视觉和 Core 语义边界；
6. **相机定位**：后期奖励还是首周留存；由此决定补梦风铃成本和入口发现；
7. **相机与 Pibo 的关系**：是否采用“共餐／地球食物观察”，以及首期是否只做一次观察行为；
8. **受苦边界替代决定**：严重度、恢复、缺数据、未打开 App 和通知规则；
9. **记忆的最小定义**：只记录能力获得和首次事件，还是增加重复生活模式；
10. **极简 MVP 范围**：相机与 Walk Doodle 本次是否保持 Release 开启。

这些问题未确认前，可以继续做诊断工具、原型和视觉探索，但不应新增第二套状态、货币、
关系数值或惩罚规则。

## 10. 建议验证顺序

### P0：先验证核心循环

1. 真机用真实睡眠和运动验证状态事实；
2. 补齐并验收精力充足正式视觉；
3. 在无文字情况下验证稳定／疲惫／精力充足可辨认；
4. 验证一个状态对应一个照料动作；
5. 跨自然日形成并拔取第一枚 `bo`；
6. 用第一枚 `bo` 解锁吊床并立即看到 Pibo 使用它。

### P1：把相机接入共同生活

1. 解锁补梦风铃；
2. 拍摄一餐并返回森林；
3. 复用食物抠图让 Pibo 观察；
4. 识别成功、失败、退出和重拍都保持幂等；
5. 确认相机不影响 `bo` 和主健康状态。

### P2：再验证长期扩展

- 每个物件是否都带来一个 Pibo 自主行为；
- 足迹是否能成为共同生活回看；
- Walk Doodle 是否值得首发；
- Shadow Pibo 是否在单好友、隐私可控前提下成立；
- 主线事件 04 是否仍然需要独立剧情节点。

## 11. 验收指标建议

产品是否成立，优先看行为而不是功能完成率：

- 新用户能否在五秒内说出“我的睡眠和活动会改变 Pibo”；
- 用户是否能不看状态文字分辨疲惫和精力充足；
- 用户看到状态后是否知道下一步可以做什么；
- 用户是否会主动回来查看第一枚 `bo`；
- 第一枚 `bo` 解锁吊床后，是否感到 Pibo 永久多了一种能力；
- 拍完餐食后，用户是否认为相机属于 Pibo，而不是跳出去的卡路里工具；
- 第二周打开理由是否是“看看 Pibo 怎么样”，而不是只响应通知。
