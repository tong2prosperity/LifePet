# Day 0–7 用户动线与物件检视方案

> **目标**：让用户在首日立即理解“健康数据改变 Pibo”，随后通过第一枚真实 `bo` 完成永久成长，而不是用剧情伪造健康产物。  
> **状态**：完整方案与第一枚可消费 `bo` 必须来自真实数据已于 2026-08-17 经用户确认，可进入首版改造。

## 一、设计原则

1. **首日先证明核心价值，不强求完成所有循环**  
   用户必须立即看到真实数据落在 Pibo 身上，并完成一次照料；第一枚真实 `bo` 可以在后续符合 Core 规则时成熟。

2. **按事件推进，不按固定第几天承诺**  
   用户的数据完整度和 `bo` 生长速度不同。界面使用“开始生长”“已经成熟”“可以唤醒”等事实，不承诺所有人第二天必然获得一枚。

3. **引导一次，不持续强制**  
   第一次状态互动、第一次拔取和第一次物件唤醒可以高亮提示，但用户可以稍后完成。成熟 `bo` 永不过期。

4. **基础相机是可选支线**  
   首日可见，但不插入必须完成的 Onboarding，也不要求一日三餐。

## 二、Day 0：首次打开（已确认）

### 阶段 A：先见到 Pibo

1. 用户先看到 Pibo 和固定森林，而不是先看到复杂功能列表；
2. 用一句话说明：`你的睡眠和活动，会直接影响 Pibo。`；
3. 在解释用途的上下文中请求 HealthKit 权限；通知、相机和位置不在此时打包请求。

### 阶段 B：第一次真实反馈

1. 授权后读取当前可用的真实健康事实；
2. Core 有可靠结论时，Pibo 直接进入对应状态；
3. 数据不足或权限未开放时进入 `dataUnknown`，不伪装为稳定，也不阻塞进入首页；
4. 首次短提示只回答：`Pibo 现在怎么样`。

### 阶段 C：第一次照料

1. 短暂提示用户点击 Pibo；
2. 根据当前状态执行一个上下文动作；
3. Pibo 必须产生姿态、位置或环境使用的可见变化；
4. 点击不改变底层健康状态。

### 阶段 D：解释 `bo`，但不赠送假库存

1. 镜头或微光提示 Pibo 身上的 `bo` 生长位置；
2. 文案说明：`从完整记录的生活开始，能量会在这里慢慢凝成 bo。`；
3. 不直接生成成熟 `bo`，不向账本写入剧情奖励；
4. 在尚未进入计分边界时，不伪造生长进度。

### 阶段 E：进入自由首页

- 用户可以继续观察 Pibo；
- 右上角基础相机按钮已经可见，但不强制拍摄；
- 森林一次只显示下一个未唤醒物件；它直接以灰态存在，点击才展开功能与成本，不另设进度窗口或物件目录；
- 首次会话在完成一次照料后已经成立，不要求停留五分钟。

## 三、第一个完整健康周期（已确认）

从现有账本允许的第一个完整自然日开始：

1. 真实睡眠和活动继续改变 Pibo 主状态；
2. `growthProgress` 开始推动头顶 `bo` 的发芽和成形；
3. 用户再次打开时，首先看到的是 Pibo 与上次不同的状态或 `bo` 阶段；
4. 如果进度尚未成熟，只展示当前事实，不承诺具体剩余天数；
5. 相机继续作为可选共同观察，不产生 `bo`。

## 四、第一枚真实 `bo` 成熟（已确认）

1. 用户进入首页时，成熟 `bo` 在 Pibo 身上有清晰的可拔取表现；
2. 第一次显示轻量手势提示，用户也可以点击完成；
3. `bo` 飞入容器并显示准确库存 `1 bo`；
4. 森林中一直存在的灰态吊床此时已可用第一枚真实 `bo` 唤醒；
5. 用户可以立刻检视，也可以稍后处理；成熟与库存都不会过期。

## 五、物件检视与第一项永久成长（已确认）

### 5.1 检视面板

用户点击未唤醒吊床后，底部出现轻量 Half-sheet：

- 标题：`吊床（未唤醒）`；
- 功能：`唤醒后，Pibo 睡觉或疲惫时可以使用吊床。`；
- 数量：`需要 1 bo · 当前 1 bo`；
- 主按钮：`唤醒吊床`；
- 不足时：`还需要 1 bo`，按钮禁用。

不使用“共振需求”“未唤醒的遗迹”等必须二次理解的词代替核心功能信息；世界观可以通过画面、动画和一行补充说明表达。

### 5.2 唤醒结果

1. 用户确认后，永久扣除准确数量的 `bo` 并写入物件所有权；
2. 同一个森林节点从灰态变为正常状态，不打开独立解锁结果窗口；
3. 以后自然进入 `sleeping` 时优先使用已拥有的吊床；
4. 物件所有权继续开放现有睡眠回顾和通知能力；
5. Pibo 当场跑去检查／首次使用的专门动作留到该动作与行为重新设计时实现。

这一步才是首版第一个完整养成闭环：

```text
真实健康 → bo → 吊床 → Pibo 永久学会新行为
```

## 六、首周后半段（已确认）

首周不以强制日历任务驱动，而以用户实际达到的里程碑推进：

- 继续观察不同健康事件如何改变 Pibo；
- 在不同状态下执行对应照料；
- 看到吊床从一次解锁变成 Pibo 的日常自主行为；
- 可选使用餐食相机，看到食物回到森林；
- 继续积累下一枚 `bo`，但首版首页一次只展示一个明确的下一目标。

现有后续物件价格 `5 / 5 / 15 bo` 暂不在首版改造中重算。基础相机先从补梦风铃门控中解耦；其他物件的成本、顺序和补梦风铃新价值在第一枚 `bo` 闭环确认后再审批。

## 七、Day 0–7 不做的事情

- 不赠送或伪造第一枚可消费 `bo`；
- 不要求连续签到；
- 不要求拍满一日三餐；
- 不因没有打开 App 让 Pibo 冰封；
- 不展示完整物件商店或长期能力树；
- 不把 HealthKit、通知、相机、位置权限一次性打包索取；
- 不承诺固定日期必然成熟，避免数据差异造成失信。

## 八、异常插入点（已确认）

- Day 0 无健康权限／无可靠数据：进入 `dataUnknown`，用户仍可进入首页；
- HealthKit 暂时中断：展示异常状态与可点击说明，不只发一次 Toast；
- 相机或网络瞬时失败：使用 Toast／Banner，保留可恢复操作；
- 所有异常都不能生成假记录、扣除 `bo` 或改变 Pibo 为负面健康状态。

## 九、后续记录但暂不验收的指标

- 用户是否在五秒内理解健康数据会改变 Pibo；
- 是否完成第一次上下文照料；
- 是否在第一枚 `bo` 成熟后回来拔取；
- 唤醒吊床后是否理解 Pibo 永久学会了新行为；
- 相机使用后是否认为它属于与 Pibo 的共同生活；
- D1、D3、D7 的回访行为。

这些指标先记录，不作为本轮产品审批和代码启动的前置阻塞项。
