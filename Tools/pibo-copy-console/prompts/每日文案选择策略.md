# Pibo 每日文案选择策略

## 目标

让用户每天打开 Pibo 时，在相同真实情境下尽量遇到不同的互动单元；允许长期重复，但避免同一天、连续几次和近几天重复。结果必须在 iOS/HarmonyOS 一致、可离线、可复现、不能因为随机数破坏微章节。

## 选择顺序

1. Core 先按真实健康事实、主状态、行为和事件确定唯一 context；每日策略不能改变触发资格。
2. 如果有未完成微章节，永远继续该单元的下一句；不能为了“今日不同”中途换单元。
3. 在当前 context 的全部已审核单元中，计算每日种子：用户稳定匿名标识 + 本地自然日 + context key + 内容版本。只将这些值输入 Core 的确定性哈希，不上传、不使用原始健康数据。
4. 用每日种子生成一个当天的确定性排列，从排列中选择候选。这样同一天不同设备可以得到相同方向，App 重启也不会重新抽到另一句。
5. 过滤近期已显示过的单元：同一天优先不重复，近 3 天尽量不重复，近 7 天尽量不重复。历史按 context 保存最近显示的内容指纹，不保存完整台词到健康记录。
6. 若候选池大于过滤后的池，选每日排列中第一个未命中的单元；若池被耗尽，放宽到 3 天，再放宽到 7 天，最后才选择最久未显示的单元。小池不会因此无话可说。
7. 只有微章节最后一句显示完成后，才把该单元写入“已完成”历史并消费事件；开始后中断不能让下一次直接跳到别的句子。
8. 不同 context 分开计算和去重。例如刚跑完步的情境不应该因为昨天说过 stable.idle 就被过滤。

## 为什么不使用纯随机

纯随机会导致同一天连续重复、冷启动每次重抽、两个平台结果不同、微章节中途跳句。每日确定性排列仍然有新鲜感，同时可以测试、回放和解释；近期历史过滤负责减少重复。

## 参数建议

- 同一天：严格不重复，除非该 context 只有一个单元。
- 近 3 天：强过滤。
- 近 7 天：软过滤；池小于 8 个时不强行等待。
- 近 30 天：只记录内容指纹用于统计，不阻止显示。
- 内容版本改变时，版本加入种子；新增单元会自然获得机会，旧历史仍可用于短期去重。
- stable.touchDiscovery 不走每日选择，固定三单元顺序；sleeping.asleep 可按每日排列选择单句，但不组成微章节。
- 事件型 context 先保证事件回应，再应用情境内去重；不能因历史过滤而跳过真实健康事件。

## 防止“每天打开就播放”

每日种子只决定“当天第一次真正有文本机会时的候选顺序”，不主动开口、不绕过双击、不绕过三秒文本冷却，也不改变 Core 的事件优先级。用户没有发生有效拍击时，不写显示历史。

## 必须进入 Core 的原因

文案选择、确定性随机、内容版本、微章节继续和跨端去重都是共享领域规则。不能只在 ArkTS 或 Swift 中实现，否则两个平台会产生不同台词，也不能在控制台或 JSONL 中加入 weight/probability/id 让平台自行抽签。

## 当前状态

已生成 467 个单元的合并候选并完成格式校验；当前 Core 仍是持久 cursor 的顺序选择，尚未启用每日排列和近期开口历史。本策略需要先在 pibo-core 实现、测试并发布 SemVer 版本，再由 HarmonyOS 接入，随后 iOS 对齐。合并文件不会在该策略发布前直接覆盖正式资源。
